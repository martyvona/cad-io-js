# Corpus checks

Scripts that run this repository's code against the real-world test corpus: 517 Part 21 files, 421 MB, 4.9 M instances (see `../test_corpus/README.md`). They complement the package tests (`npm test`), which use small inline fixtures and don't need the corpus. Each step of the work added the check that verified it (the Step column: phase and step, as the history in `git show V0.1.0:CLAUDE.md` lists them); each check's last results are in its `.log` beside it, and what they found is summarized in `../CLAUDE.md`.

## Setup

Fetch the corpus once with `../test_corpus/third_party/pull.sh`. The scripts find it relative to the repository, so they run from any directory; a check stops with a hint to run `pull.sh` if listed files are missing. The checks that read the whole corpus take an optional list file in place of `../test_corpus/files.txt`, one path per line relative to `../test_corpus/third_party/`.

**Several files at once** (`runner.ts`): the slow checks run their files in persistent child processes (`runner-child.ts`), each loading the check once, the results merged in file order so the log doesn't depend on how many run. `CHILDREN` sets how many (default a third of the hardware threads, at most one per 4 GiB of memory: 3 on a 10-core M4, 9 on a 28-thread i9-9940X with 62 GiB), `MESH_WORKERS` each one's meshing workers (default: the threads but one, less one a child, shared out), so no thread waits for a core; the children's largest peak memory goes to standard error at the end (`runner: ...`), for sizing them. Files are handed out largest first within a memory budget: a file starts only while the running files' estimates (`MEM_FACTOR` x its size, default 15, a gzipped file's uncompressed size; plus `MEM_CHILD_BASE` GiB a child, default 0.5) stay within `MEM_BUDGET` GiB (default 24), else the largest that fits starts, or none until one ends, a file alone always starting; the terms go to standard error at the start, the count of files that waited at the end. Largest first alone started coverage_corpus's six largest files together (two copies of LMP1, 271 MB) at 17-19 GiB in all in the first minute, no child over 6 GiB; their estimates total 13.0 GiB with the children's base, so the default budget doesn't hold any back on 6 children, and the estimate is STEP parsing's (LMP1's import alone 3.8 GiB, 15 x): with meshing the six peaked at 17.3 GiB, 1.33 x their estimates, and at `MEM_BUDGET=10` (LMP1.stpZ held back until LMP1.step ends) the other five at 14.1 GiB, 1.53 x. On the i9, `gltf_corpus` took 179 s with 3 children (8 workers each), 119 s with 6, 110 s with 9 and 109 s with 13 (one worker each); `roundtrip_corpus` with 9 children peaked at 5.75 GiB in one child (its largest file) and 21 GiB in all. The checks that don't mesh in workers (`brep_geometry`, `area_model`, `scene_occt`, `step_roundtrip`) get the same third, though the meshing workers' threads go unused: in two of them the largest file sets the time (`bug29979_firetherm_12.step`, 124 s of `brep_geometry`'s 134 s), and more children only slow it (`brep_geometry` 139 s with 15, 151 s with 27; `area_model` 129 s with 9, 147 s with 27), while `step_roundtrip` gained 11% with 18 (218 s against 244 s). Two thirds for such checks, or a count per check, were the alternatives; one rule was kept, `CHILDREN` overriding it for a run. OCCT's own messages (`*** ERR ...`), printed by the children as they come, are in the log in an order that varies from run to run; a part can still mesh slower than with one check alone (an Apple M4's 10 cores include 6 slower efficiency cores: `bug24024_slow_import.stp`'s largest part took 29 s in one run, 64 s in another), so timeouts need room (the pool's default 120 s; that part timed out at 60 s); `CHILDREN=0` runs every file in the main process, as before. A converted check exports `check` (its per-file part: `setup`, `file`, `teardown`) and runs its main only when run directly. Converted: `stepconv_corpus.ts` (44 min to 21 with 3 children), `roundtrip_corpus.ts` (33 to 16; all its processes together 9 GB at most), `truck_occt.ts` (18 to 7.5), `step_route.ts` (13 to 6; its planted parts picked by a hash of each part's file and id, about one in 10). Converted besides: the exporters' checks (`export_view.ts`, `gltf_corpus.ts`, `threejs_corpus.ts`, `threemf_corpus.ts`), `weld_survey.ts`, `scene_occt.ts`, `area_occt.ts`, `area_model.ts`, `brep_geometry.ts`, each about twice as fast. Checks whose per-file results are additive tallies merge them with `addInto`. Planted bugs go into parts (or faces) picked by a hash of where they are (`corpus.ts`'s `plantedPart`), so a file's planting doesn't depend on the files before it.

**Rounds** (`round.ts`, `mesh-cache.ts`): checks run one after another sharing a mesh cache in `workdir/mesh-cache/` (`MESH_CACHE`, which the round sets; `MESH_CACHE_MB`, default 32 GiB), emptied when the round starts (only a directory holding the round's marker file, `.corpus-mesh-cache`), so a round starts from fresh meshing: its first check that consumes meshes meshes the corpus at its settings, and the others at the same settings read it, timeouts included. The consumers mesh through `mesh-cache.ts`'s `cachedMesher` (`stepconv_corpus` also gives `stepconv` `--cache`) and print the cache's hits and misses on standard error, not in their logs; the checks of meshing itself never use it. Entries are shared by deflections: the six checks at the coarse profile share theirs (edges don't change the key), `stepconv_corpus` (the medium profile) has its own. A planted bug in an imported model changes its key; `roundtrip_corpus`'s plants come after meshing. Usage in `round.ts`'s header; logs in `workdir/round-<time>/`.

`cache_check.ts` and `truck_bench.ts` tessellate phase 0's per-part subsets instead: make them once with `make_subsets.ts` (the commands are in its header) into `../test_corpus/subsets/` (git-ignored).

## Reference outputs

The `.log` files are the outputs the progress document cites. A fresh run's first line is its host (`host: ...`; logs made before there was one lack it), so drop it from both before comparing; then diff everything but the lines with timings (line 2 of the writer and JSON logs, line 1 of the parser, binding and semantic logs; the OCCT checks print no timings), for example (`h` drops the host line):

```sh
h() { grep -v '^host: ' "$1"; }
node corpus_checks/semantic_corpus.ts > /tmp/s6.log && diff <(h corpus_checks/semantic_corpus.log | sed 1d) <(h /tmp/s6.log | sed 1d)
node corpus_checks/bind_corpus.ts > /tmp/b.log && diff <(h corpus_checks/bind_corpus.log | sed 1d) <(h /tmp/b.log | sed 1d)
node corpus_checks/json_corpus.ts > /tmp/j.log && diff <(h corpus_checks/json_corpus.log | sed 2d) <(h /tmp/j.log | sed 2d)
node --max-old-space-size=12000 corpus_checks/step_geometry.ts > /tmp/g.log && diff <(h corpus_checks/step_geometry.log | sed 1d) <(h /tmp/g.log | sed 1d)
node corpus_checks/number_kinds.ts > /tmp/n.log && diff <(h corpus_checks/number_kinds.log) <(h /tmp/n.log)
node corpus_checks/writer_corpus.ts > /tmp/w.log && diff <(h corpus_checks/writer_corpus.log | sed 2d) <(h /tmp/w.log | sed 2d)
node corpus_checks/parser_corpus.ts > /tmp/p.log && diff <(h corpus_checks/parser_corpus.log | sed 1d) <(h /tmp/p.log | sed 1d)
node corpus_checks/schema_corpus_check.ts > /tmp/s.log && diff <(h corpus_checks/schema_corpus_check.log) <(h /tmp/s.log)
node corpus_checks/schema_xdict.ts corpus_checks/schema_corpus_check.log
node corpus_checks/parser_bench.ts gkv311-opencascade-dataset/step/bug31711.stp gkv311-opencascade-dataset/step/Median_cx-fs01_bicycle.stp
```

A difference means either a code change or a corpus update; `../test_corpus/README.md` records the corpus versions the logs were made with.
