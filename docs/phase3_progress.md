# Phase 3 (the backends): plan and progress

*Paths in this document are relative to this `docs/` directory.*

Phase 3 of `architecture.md` ("Phasing"): the tessellation backends, OCCT first, then truck, tested against OCCT. The OCCT backend was brought forward into phase 2 (`phase2_progress.md`, step 4, decision 5) and already passes the end-to-end check, so this phase is mostly the truck backend, plus the host-side machinery both backends need (workers, a watchdog, instance recycling, caching), plus the OCCT loose ends phase 0 and phase 2 left open. This file tracks the order of work and what each step finds.

## Where things stand

- **OCCT backend** (`../packages/tess-occt`): the `Tessellator` interface with face ids, edges, file units and the request origin; 99.1% geometric and 97.8% colour agreement with `occt-import-js` over the corpus (`phase2_progress.md`, step 5). Open: the 62 geometrically bounded surface representations it returns no shape for and the 16 "no shape" errors, instance recycling (OCCT's heap never shrinks), and phase 0's slow `BRepMesh` faces (bicycle #2022). *(Step 5 classified the first two and tuned recycling; the slow faces are still open.)*
- **truck** (`../phase0_tessellation_spike/truck_spike`): phase 0's prototype, about 120 lines of Rust over truck `88ed005`, tessellates every shell in a subset and reports face ids by mirroring the `filter_map` in truck's `shell_faces`. It returns unindexed triangles as JSON, with no normals, edges, origin or root. Robustness against OCCT 8.1: 144 of 188 parts within 5% of OCCT's area; 6 panics (`circle.rs:65`, tolerance below 1e-6 on inch parts), one hang over 10 minutes (`trj2_as1-id-203` #891), 93 empty faces. 263,902 bytes brotli, about 1/6 of OCCT.
- **truck upstream** has only a dependency upgrade (`c2a1da8`, 2026-10-12) since our pin, so none of those problems has been fixed upstream.
- **`tessellateScene`** (`../packages/cad-scene/src/tessellate.ts`) runs one request at a time on the calling thread, with no timeout and no cache.

## Decisions (made by the user, 2026-10-17)

1. **Where the worker host lives. Decided by the user (2026-10-17): a new package, `tess-workers`**, so `cad-scene` stays pure data and types. (Alternative: in `cad-scene`, next to `tessellateScene`.) The one package serves both environments:
   - the pool, timeout, recycling and request routing are written once against a small worker handle (`post`, `onMessage`, `onError`, `terminate`);
   - two adapters implement the handle, one over `worker_threads` (Node has no global `Worker`) and one over Web Workers, plus the matching worker-side entry (`parentPort` against `self`);
   - `package.json` conditional exports pick the adapter (`"node"` → the `worker_threads` one, `"default"` → the Web Worker one), so browser bundles never see `worker_threads`.
2. **How truck's tolerance maps onto the request.** truck takes one absolute distance (`tol`, in file units); the interface also has an angular deflection. **Decided by the user (2026-10-17): `tol = linearDeflection`, the angular deflection ignored** (noted in the backend's `info`). Meshes of small round features come out coarser than OCCT's at the same request, and triangle counts differ (phase 0: 1.23 M against OCCT's 0.81 M on the bicycle, at 0.05 mm against 0.05 mm / 0.5 rad). (Alternative: also bound the angle by lowering `tol` per face from its curvature, `r (1 − cos(θ/2))` for radius `r`; closer to OCCT's meshes, but more wrapper code, and truck applies one tolerance per shell, so per-face control may need a call per face.)
3. **truck's known failures.** **Decided by the user (2026-10-17): small workarounds in our wrapper where feasible** (for example, checking each circle's radius against the tolerance before meshing and raising the tolerance locally, to avoid the circle-tolerance panic; keeping the face-id mirroring), **and no upstream reports for now.** Each failure, workaround and repro subset is documented here instead, and how to work with the truck project is decided later. Whatever the workarounds don't cover, the host's trap recovery and watchdog turn into diagnostics. truck itself is not patched (no fork). (Alternative: upstream reports only, with no workarounds.)
4. **Caching. Decided by the user (2026-10-17): in phase 3 (step 4), with a configurable maximum size, in Node and in browsers, that can be set to 0 to disable caching.** (Alternative: deferred to phase 4's `stepconv`.)
5. **`curves` parts. Decided by the user (2026-10-17): in phase 3 (step 6).** (Alternative: left in the backlog.)
6. **The OCCT build variant. Decided by the user (2026-10-17): `-Os` without the `VBernstein` patch**, which isn't worth maintaining for now (2.18 against 1.71 MB brotli). The patch stays documented in `../phase0_tessellation_spike/phase0_results.md` ("Build variants") in case the download size matters later.

## Step 1: the worker host

`../packages/tess-workers` (Apache-2.0; depends on `cad-scene` only):

- **`pool.ts`, `PoolTessellator`:** a `Tessellator` that runs a backend in workers, written against a small `WorkerHandle` (`post`, `onMessage`, `onError`, `terminate`, and in Node `ref`/`unref`). The backend is named by module and export (`{module, export, options}`; the module an absolute URL, e.g. `import.meta.resolve('tess-occt')`) and constructed in each worker. One request per worker at a time, first come first served. Options and defaults:

  | Option | Default | Meaning |
  |---|---|---|
  | `workers` | hardware concurrency − 1, at least 1 | pool size; workers start as requests arrive (`init()` starts the first, which reports the backend's `info`) |
  | `timeoutMs` | 120,000 | per request; the worker is terminated and the request rejected. 0: none |
  | `maxPartsPerWorker` | 0 (never) | recycle a worker after this many parts |
  | `maxMemoryBytes` | 256 MiB (1 GiB until step 5) | recycle once the backend reports more (`memoryBytes()`, below) |

  A worker is also replaced after any error its backend throws, since a WebAssembly trap (a Rust panic, say) can leave the instance broken, and after it exits or fails; its request is rejected and the queue carries on. A replacement that can't load the backend fails the queued requests only when no other worker is alive, and no further worker starts until one is ready, so a broken backend doesn't respawn forever. Idle workers are `unref`'d in Node, so a pool that isn't disposed doesn't keep the process alive. `dispose()` terminates everything and rejects what's pending. `maxMemoryBytes` was tuned in step 5; the others are placeholders.
- **The two environments** (decision 1): `node.ts` (`worker_threads`) and `browser.ts` (module Web Workers), each with its worker entry (`worker.node.ts`, `worker.browser.ts`, both calling `serve.ts`) and exporting the same `WorkerTessellator`; `package.json` picks one by the `"node"` and `"default"` export conditions. The Node adapter leaves `--input-type` out of the flags workers inherit, since with it (`node -e`) a worker's file entry fails to load.
- **`serve.ts`, the worker side:** imports the backend, then answers each request, transferring the result's buffers rather than copying them (requests are copied, so the caller keeps its payload).
- **Interface addition** (`cad-scene`): the optional `Tessellator.memoryBytes()`, the backend's memory (WASM linear memory, which never shrinks); `OcctTessellator` implements it.
- **`tessellateScene`** gains `concurrency` (requests in flight at once, default 1; set it to the pool's size). Meshes and diagnostics stay in part order whatever order the parts finish in; `onPart` reports in finishing order.

**Tests** (14 new, 90 in the repo): 11 pool tests on a fake backend whose payload picks its behaviour (a result, a hang, a WASM trap, memory growth, a delay, the worker exiting), naming its instance in each result so the tests see replacements: parallel results, the timeout, a trap and an exit (each with a request queued behind), recycling by parts and by memory, init failures, a replacement that can't load (alone, and while another worker is busy, counting the workers started), dispose, and a child Node process that must exit with an undisposed pool. One test runs `tess-occt` in two workers, a fresh one per part, through `tessellateScene` with concurrency 2, and gets meshes and diagnostics identical to OCCT on the main thread (`as1-oc-214-mat.stp`, 5 parts; an instrumented run confirmed 5 workers started and 2 requests in flight). Two `cad-scene` tests check `tessellateScene` at concurrency 1 and 3 (requests, units, the order of results and diagnostics, a failed part).

**Mutation check:** 17 deliberate bugs in the pool, the worker side, the Node adapter and `tessellateScene`, all caught. Two survived the first round, both from weak tests: the exit test queued its follow-up request before the crashing one, and no test had a replacement fail to load while another worker was alive (the only case where blocking further starts matters); both tests were fixed.

**Browsers:** `npm test` runs in Node, which has no Web Workers, so `../packages/tess-workers/test/browser-check.ts` (run by hand: `node packages/tess-workers/test/browser-check.ts [chrome]`) serves the sources with their types stripped (`module.stripTypeScriptTypes`) and runs six of the scenarios in headless Chrome: parallel results, the timeout, a trap, recycling, init failure and a missing backend module. All pass in HeadlessChrome 155. With the adapter mutated to start classic instead of module workers, all six fail, through the `onerror` path. Not checked: Firefox and Safari.

## Step 2: the truck backend

`../packages/tess-truck` (Apache-2.0):

- **`native/`, the Rust wrapper** (`src/lib.rs`, 554 lines), over truck `88ed005` by path (`../third_party/truck`, unchanged; no fork). It parses the payload with truck's own parser (ruststep), reads the root representation's `items` itself (simple or complex instance), and meshes the shells of each `MANIFOLD_SOLID_BREP` (and `BREP_WITH_VOIDS`), `SHELL_BASED_SURFACE_MODEL` or shell among them; other items (a `GEOMETRIC_SET`, say) are listed in a warning, placements ignored. Without a `rootId` it meshes every solid and surface model. Output:
  - an indexed mesh: truck's per-corner attributes welded into vertices per face, by position and normal; normals from the surface, flipped with the face;
  - faces by `ADVANCED_FACE` id (an `ORIENTED_FACE` reports the face it orients), in shell order;
  - edges by `EDGE_CURVE` id: truck's meshed edges are polylines whose points the face meshes reuse exactly (the triangulation keeps boundary points as given), so edge points are mesh vertices. Kinds from the topology (used by two faces: shared; twice by one face: seam; once: free; all points coincident: degenerate), and the dihedral angle of shared edges from the two faces' normals at the edge's points;
  - positions minus the request's origin in double precision, then `Float32`; ids above 2³¹ − 1 come back as null (as in the OCCT wrapper, which also uses `Int32`).
  - The tolerance is `linearDeflection` (decision 2).
- **A plain C ABI** (`tess_run`, `tess_ptr`/`tess_len` for each result array, `tess_free`, `tess_alloc`), like the OCCT wrapper's, instead of wasm-bindgen: one `.wasm` file and no generated glue. truck's dependencies still leave five wasm-bindgen runtime imports in the module (from chrono and getrandom, which truck enables for wasm); nothing on our path calls them, and `src/index.ts` supplies stubs that throw if anything does. A test pins the module's import list, so a change shows.
- **`build.sh`:** `cargo build --release --locked --target wasm32-unknown-unknown` (`panic = "abort"`, LTO) and `wasm-opt -O` (from `PATH`, or wasm-pack's download). 1,505,702 bytes, 312,068 brotli; phase 0's spike was 263,902 brotli. Optimizing for size is to be weighed against speed in step 3.
- **`src/index.ts`, `TruckTessellator`:** loads `dist/tess_truck.wasm` (from the file system in Node, by `fetch` elsewhere, or bytes or a URL in `init({wasm})`), runs requests and reports truck's diagnostics: faces and edges it can't convert, faces it fails to mesh, items it doesn't mesh, and placements fixed (below). **Panics:** a panic hook passes truck's message out through an import before the module traps; the request returns an empty result with an error diagnostic (`truck panicked: …`), and the instance is replaced (re-instantiated from the compiled module, a few milliseconds), so a panic costs only its own part, with or without the worker pool. truck can also hang; only the pool's timeout (step 1) covers that.

### Workarounds (decision 3)

1. **Shells are built by the wrapper**, not by truck's `Table::to_compressed_shell`, so each face and edge keeps its STEP id. Reading truck's code (`truck-stepio/src/in/convert.rs`) shows two problems the wrapper avoids, neither yet seen in our corpus (step 3 will count): truck numbers a vertex or edge before converting it, so one that fails to convert shifts every later index in the shell (faces would then use the wrong edges); and it drops faces it can't convert without saying which (phase 0 mirrored its filter to recover the ids). Here a face whose surface or edges don't convert is left out and reported by id.
2. **`AXIS2_PLACEMENT_3D` without a `ref_direction`.** The phase 0 panics (`tolerance must be no less than 1e-6` in truck-geometry `specifieds/circle.rs`, on 6 parts of `nist_stc_07` and `trj7_k1-ct`) are not about small tolerances, as phase 0 guessed: truck defaults a missing `ref_direction` to (1, 0, 0) even when the axis is ±(1, 0, 0) (`truck-stepio/src/in/mod.rs`, `From<&Axis2Placement3d> for Matrix4`). The placement's x axis is then the normalized zero vector, NaN, and the tolerance check fails on NaN. ISO 10303-42 (`first_proj_axis`) prescribes (0, 1, 0) in that case. The wrapper adds a `DIRECTION` (0, 1, 0) and points such placements at it, in the parsed file before truck reads it, and reports how many (an info diagnostic): 26 in `trj7_k1-ct-214.stp` #1926, 72 in `nist_stc_07_asme1_ap242-e3.stp` #11020. Both parts now mesh: #1926 fully (area within 0.6% of OCCT's), #11020 with 288 of 304 faces (16 small faces fail to mesh; area within 0.1%). A first attempt, raising the tolerance above 1e-6 × the largest radius, didn't help and was removed.
3. **Shells that face the wrong way are reversed** (decided by the user, 2026-10-18, below), as OCCT's shape healing does (`ShapeFix_Solid`, `CreateSolids`: each closed shell is put alone in a solid and the point at infinity classified; an outer shell with infinity inside, or a void with infinity outside, is reversed). The wrapper does the equivalent on the mesh with the divergence theorem: the signed volume of a closed triangle mesh, Σ a · (b × c) / 6, is positive when its triangles face outward. After meshing, each solid shell (a solid's outer shell or a void; surface models' shells are left alone) whose mesh is closed (every face meshed, every edge used twice) is reversed when the sign is wrong: negative for an outer shell, positive for a void. STEP says which shells are voids, so OCCT's containment analysis isn't needed. An info diagnostic names each reversed shell, and another lists solid shells whose mesh isn't closed, which are left as written.

## Step 3: truck against OCCT

**`../corpus_checks/truck_occt.ts`** (log `truck_occt.log`) runs every brep part of every corpus file up to 30 MB (515 files; `bug29979_firetherm_12.step` and `bug31711.stp` are larger) through the truck backend and our OCCT backend, each in a `tess-workers` pool (4 workers; timeouts 60 s for truck, 300 s for OCCT), at 0.05 mm (phase 0's tolerance; OCCT also 0.5 rad), and compares them part by part, and face by face where both mesh a part. `DUMP=<dir>` writes every problem part's subset, for repros (1,291 files, 177 MB, in the git-ignored `../corpus_checks/truck_repros/`). It replaces phase 0's three oracles: the area check is kept per part; the face ids are compared directly with OCCT's (the vertex-based check was only needed while ids came from mirroring truck); the bare-against-wrapped check no longer applies, since the wrapper reads the root representation itself. **`../corpus_checks/truck_bench.ts`** times truck builds and OCCT single-threaded over phase 0's subsets.

The run found eight more truck failures with workarounds, all now in the wrapper (decision 3), and showed that comparing orientation and area with OCCT confuses truck's errors with OCCT's healing and with the meshes' different chords. So the per-face comparison is geometric and topological:

- **Geometry:** up to 10 vertices of each face sampled from each mesh, against the other mesh's triangles of the same face (by entity id), within twice the tolerance. A truck vertex off OCCT's face means truck's surface is wrong or extends too far ("wrong"); an OCCT vertex off truck's face means part of the face is missing ("short"). Per-face area, the first measure, flagged many small fillets merely for their chords (at 0.05 mm, a fillet of 0.2 mm radius loses about 10% of its area to either mesher); all such cylinders and tori pass the geometric test.
- **Orientation against the file's own loops:** truck's triangles wind counter-clockwise about its normals, and ISO 10303-42 orients a face's loops counter-clockwise about the face normal, so each loop edge, traversed as the loop uses it, should run along the face's own triangle boundaries. A face whose loop edges all run the other way has a normal that contradicts its loops ("contra"). This needs no OCCT: comparing with OCCT turned out to measure OCCT's healing (below) as much as truck.

### Workarounds added (decision 3)

4. **`SURFACE_CURVE`s are read by their 3D curve**, as OCCT does (`StepToGeom::MakeCurve` takes `Curve3d()` whatever the `master_representation`). truck follows a `.PCURVE_S1.` or `.PCURVE_S2.` master and evaluates the pcurve on its surface, which in many files yields NaN; 11,986 surface curves in the corpus are switched.
5. **Edges and faces that evaluate to NaN are left out.** truck subdivides a curve until each piece is within the tolerance, to a depth of 100 halvings (`truck-geotrait/src/algo/curve.rs`, `sub_parameter_division`), so a curve that yields NaN anywhere is divided without end: memory grows by about 400 MB/s natively, and in WebAssembly the allocation fails at 4 GiB and traps, without a panic message (the first run's 19 "unreachable" traps). The same happens when meshing along a bounded surface's range edges. The wrapper samples each edge's curve (33 points) and each bounded surface (17 × 17) and leaves out what isn't finite, reporting it. After workaround 4, what remains are B-splines with unclamped ("periodic") knot vectors, which truck evaluates over their whole knot range instead of the valid inner range: 11 edges and 24 faces in the corpus. Clamping them recovers them (step 3b, workaround 10); the guard stays for invalid files.
6. **Instances truck's parser can't read are left out**, and the rest read. ruststep fails the whole file on the first instance it can't tokenize, such as an empty list `()`, which Part 21 allows (an `ADVANCED_FACE` with no bounds, a `TRIANGULATED_FACE`), and on malformed instances (`bug26451_Test_STEP.stp`). When the whole file fails, the wrapper splits the DATA section into instances (outside strings and comments) and tokenizes them one at a time: 868 instances left out across the corpus, which turned the first run's 50 parse errors into partial or empty results.
7. **Negative torus radii are taken as absolute values**, as OCCT does (`StepToGeom::MakeToroidalSurface`): one writer gives spindle tori a negative major radius, and truck's `Torus::new` panics on it (6 tori, 3 parts).
8. **Cone semi-angles are converted to radians** from the plane angle unit of the root representation's context (often a conversion-based `DEGREE`); truck has no unit handling and builds the cone from `tan(semi_angle)`. 2,092 cones in the corpus; cone faces off OCCT's geometry fell from 224 to 86.
9. **A shell is reversed only if its mesh is consistently oriented** (workaround 3 refined): no boundary segment traversed the same way by two triangles. The first run reversed 47 shells, most of them wrongly: where truck orients a few faces against their neighbours, the signed volume is meaningless, and reversing then flipped every correct face (1,256 of the 1,469 faces facing opposite to OCCT were in reversed shells). Now 15 shells are reversed (the round 8 voids of step 2, `brep_wv1.stp`, outer shells in `trj3_s1-al-214.stp` and others) and 236 are reported unchecked for disagreeing faces, besides 155 with open meshes. *Correction (step 3b):* this said each of the 15 agreed with OCCT afterwards; three did not (the outer shells of `trj3_s1-pe-203.stp`, `trj4_s1-pe-203.stp` and `trj3_s1-id-203.stp`, 81 faces), which step 3b's guards now leave as written.

Two smaller fixes: a NaN edge is no longer also counted as unconverted, and the panic test now uses an explicitly invalid file (a B-spline with descending knots, which truck unwraps into a panic; not seen in the corpus), since the earlier fixture no longer panics.

### Workarounds added (decision 3)

10. **Unclamped B-splines are clamped** (`clamp_curve`, `clamp_surface`: B-spline and rational curves of edges, and B-spline and rational face surfaces). A B-spline of degree p is valid only between its p-th knots from either end, [u_p, u_{m-p}] (ISO 10303-42), where its p + 1 basis functions overlap fully; truck evaluates it over the whole knot vector. Clamping inserts knots at u_p and u_{m-p} (truck's `add_knot`, exact: the curve doesn't change) until each has multiplicity p, then keeps the knots from just before the last p copies of u_p to just after the first p copies of u_{m-p}, with the outer two set to u_p and u_{m-p}, and the control points between. The dropped control points shape the curve only outside its valid range, and over the valid range the basis functions don't depend on the outer two knots. Two native tests (`cargo test`) check that the result equals the original over the valid range: the rational quadratic circle of `OCC22962-dm1-oc-214.stp`, a uniform cubic needing insertions at both ends, and a surface. In the corpus: **384 edge curves and 78 face surfaces**, far more than the 11 edges and 24 faces that gave NaN. Most unclamped curves evaluate to finite points beyond their valid range, which put truck's edge points off the faces: on `B_SPLINE_CURVE_WITH_KNOTS` edges, points off the mesh fell from 15,424 to 1,811. Truck still meshes some of these faces on closed surfaces with overlapping or stray triangles: of the six clamped faces in the tests, #40 and #628 have 18% and 11% more area than OCCT's, all six lie on OCCT's faces.
11. **A face meshed against all its loops is reversed** (`loop_sense`, before the face's orientation in its shell is applied): its loop edges, traversed as the loops use them, all run against the face's triangle boundaries, and none along them. Faces with some segments each way are left as they are. 3 faces in the corpus: `trj6_k1-ec-214.stp` and `trj7_k1-ec-214.stp` #5547 (both then agree with OCCT), and #41718 in `bug33261.stp` #41791.
12. **The shell reversal (workarounds 3 and 9) is guarded by `volume_sign`**: found because step 3's run reversed three outer shells wrongly. Two causes:
    - *The mesh leaks:* where truck's face meshes leave gaps or overhang their boundaries, the volume depends on the point it is measured from (6V(r) = 6V(0) − r · N, N the sum of the triangles' (b − a) × (c − a), zero only for a mesh that closes up geometrically). In `trj3_s1-id-203.stp` #408 the sign changes with that point: measured from the first vertex, as workaround 3 did, the shell faced inward and was reversed; from the box centre it faces outward, as OCCT has it. The sign now counts only if it is the same from every point of the bounding box.
    - *A thin part:* `trj4_s1-pe-203.stp` #1138 (and its `trj3` twin) is watertight, but truck meshes face #803 3% too large inside its closed boundary (area 190.1 against OCCT's 184.5). The faces' parts of the volume nearly cancel (OCCT's 6V is 424 against face contributions in the thousands), and #803's error of 442 makes the total negative. The sign now counts only if |6V| is at least 1% of the sum of the triangles' |6V| from the box centre: 0.09% here, against 3.3% for the smallest real reversal (the void of `bug31670_russian.stp`) and 70–100% for the others.

    The 12 shells still reversed are the 15 of step 3 less those three, and 29 shells are now reported unchecked for an unclear volume. The 1% is a judgement call: a wrongly meshed face in a part whose volume is a few percent of the contributions could still mislead it.

**The corpus check's loop test** (`reversedFaces` in `truck_occt.ts`) now expects a face's normal to run against its loops where the file reverses the face in its solid (an `ORIENTED_FACE`, or an `ORIENTED_CLOSED_SHELL`/`ORIENTED_OPEN_SHELL` with `.F.`) or the wrapper reports reversing its shell. It counted those as "contra" before: the reversed voids of the round 8 files (11–12 faces each), 66 faces in `trj8_k1-ac-203.stp`, and the shells reversed by workaround 9. The 2 faces left (`Checking_Fixture_Clamping.STEP` #8281, #8483) are mixed in the wrapper's exact check (15 and 11 segments along their triangles, one against); the corpus check matches only the one segment, since others of their edge points are off the mesh.

## Step 4: caching

`../packages/tess-cache` (Apache-2.0; depends on `cad-scene` only), laid out like `tess-workers`: `src/node.ts` and `src/browser.ts`, picked by the `"node"` and `"default"` export conditions, export the same `CachedTessellator` and `MemoryStore`, plus `FileStore` in Node and `IndexedDbStore` in browsers.

- **`CachedTessellator(inner, store, { retryFailures, keepOtherVersions })`** is a `Tessellator` wrapping any other, so it composes with the rest: in front of a `WorkerTessellator`, a cached part never reaches a worker, and `tessellateScene` needs no option for it. `info`, `init`, `memoryBytes`, `timeoutMs` and `dispose` are the inner backend's; `stats()` counts hits (and of those, cached failures), misses and store failures. A store can be shared by several backends (the key names the backend), so `dispose()` leaves it open.
- **Caching is off unless the caller turns it on**: nothing caches by itself, and a caller wraps its backend in `CachedTessellator` with a store it creates. `FileStore` has no default directory; `IndexedDbStore` works without options. **Clearing** is each store's `clear()`; there's no command line yet, since no CLI tessellates until phase 4's `stepconv`, which would take options such as `--cache-dir`, `--cache-max`, `--no-cache` and `--clear-cache`.
- **The key** is `<backend>_<version>_<hash>`: the backend's name (lower case, other characters than letters and digits as `-`, at most 32), 12 hex digits of a hash of the cache format's number and the backend's name and version, then SHA-256 over the cache format's number, the backend's `info.name` and `info.version`, the request's `format`, `rootId`, `origin` (default (0, 0, 0)), `linearDeflection`, `angularDeflection` (truck ignores it, decision 2, but it's still a different request), `edges` (default false), and the payload. The prefix lets a store find a backend's entries (below).
- **Backend versions now change with every build.** `info.version` named only the upstream commit (`truck 88ed005`, `OCCT 8.1 (3d097a0328)`), so a rebuilt wrapper with a new workaround would have read the old wrapper's results. Each backend's `init()` now appends the first 12 hex digits of its module's SHA-256 (`truck 88ed005, wasm 75196734450c`). truck already read the module's bytes; `tess-occt` now reads and compiles its module itself and hands it to Emscripten's loader through the `instantiateWasm` hook (this Emscripten build ignores `Module.wasmBinary`). Hashing costs about 3 ms for OCCT's 7 MB.
- **What's stored:** an entry (a result, or the error a request threw, and the time) encoded as one byte array: a magic number, a JSON header (time; origin, faces, edges, diagnostics and array lengths, or the error's message and time limit), then a result's arrays, 4-byte aligned, in the platform's byte order (a store is local to its machine). Decoding checks the magic number and the total length, and gives each array a buffer of its own, so a caller that changes a mesh doesn't change the cache.
- **Failures are cached too** (decided by the user, 2026-10-19, so that a part that timed out or panicked isn't waited on again on every run): results with an error diagnostic (truck's panics, OCCT's "no shape"), and requests that throw a `TessellationError` or a WebAssembly trap. `TessellationError` (new in `cad-scene`) marks a failure that's the part's rather than the host's, with `timeoutMs` when it's a time limit: the worker pool now rejects a timeout with one (`timeoutMs` the pool's limit, which the pool now exposes, as `Tessellator.timeoutMs`), and a request whose backend threw a `TessellationError` or a trap in the worker with one too (the worker says which, keeping the error's limit). Other errors are the host's and aren't cached: a worker that exits or fails mid-request (it could be the machine running out of memory), a disposed pool, a backend not initialized, an unsupported format. A cached failure says so: a result gains an info diagnostic `a cached failure from <time>; retryFailures retries it`, and a thrown one is thrown again as a `TessellationError` with that appended to its message. `retryFailures: true` sends cached failures to the backend again and caches what it answers.
- **A cached timeout answers only under a limit no longer than the one that ran out:** the inner tessellator's `timeoutMs` must be set, nonzero and at most the cached limit. A run with a longer limit (or none) tries again, and its answer, a result or a timeout at the longer limit, replaces the entry. Running out of memory can depend on how far an instance's heap had grown on earlier parts, so a fresh instance might succeed; these are cached anyway (a trap can't say why it trapped), and `retryFailures` covers them.
- **A backend's other versions are deleted** when a `CachedTessellator` first sees a version (once per version, before its first request): every entry whose key has the backend's name and another version, other processes' and pages' included, since they'd never be read again. Other backends' entries stay, so truck and OCCT can share a store, and comparing them doesn't thrash it (clearing on any change of backend would). Two versions of one backend sharing a store (two builds of an application open on one origin, say) still delete each other's entries, though only when each starts. `keepOtherVersions: true` keeps them, leaving them to the least-recently-used eviction. Each store has `deleteWhere(drop)` for this.
- A store's failures never fail a request: a read that fails or an entry that doesn't decode (deleted) is answered by the backend, and a failed write or delete leaves the cache as it was; each counts in `stats().errors`.
- **Size:** each store takes `maxBytes`, evicting the least recently used entries beyond it; a value larger than `maxBytes` isn't stored, and one left from a run with a larger maximum is evicted when the store opens. **0 disables it** (decision 4): `CachedTessellator` then passes requests straight through, without computing keys, and the stores don't touch their directory or database.

| Store | Default `maxBytes` | Where | Recency |
|---|---|---|---|
| `MemoryStore` | 256 MiB | this process or page | in memory |
| `FileStore({ dir })` | 1 GiB | one file per entry, `<dir>/<last 2 hex digits of the key>/<key>` (the end, since a backend's keys share their start); no default directory | the files' modification times, which a read updates |
| `IndexedDbStore({ name })` | 256 MiB | database `cad-io-js-tess-cache` by default: bytes in one object store, size and last use in another, so opening reads only the small records | the last-use records |

`FileStore` writes each entry to a temporary file and renames it into place, so a reader never sees a partial one; temporary files over an hour old (from a process that died) are removed when a store opens. It reads and removes only files named like entries, so `clear()` leaves anything else in the directory. Several processes (or pages, for IndexedDB) can share a store: each counts the bytes held from a scan when it opens, plus what it writes and reads, so the total can run over `maxBytes` while several write at once, and an entry another deleted is a miss. Failed opens are retried on the next call.

| truck | 9.01 s | 9.03 s | 0.07 s | 0.04 s | 46.8 MB |
| OCCT | 22.46 s | 22.26 s | 0.07 s | 0.04 s | 43.9 MB |

A miss costs nothing measurable: the backend-alone run goes first, and its warm-up outweighs the key, the encoding and the write (OCCT's first cached run was faster than it in both runs of the check). A hit costs about 0.4 ms per part from files. The stored results take about 1.3 times the payload's size, with edges.

**Decided by the user (2026-10-19), on the first version of this step:** cache failures, timeouts included, with the error's message, given that the key names the exact build (it had cached neither); and delete stale entries automatically. The user's first idea was to clear the cache whenever a different backend or build was in use; the proposal adopted instead deletes only the same backend's other versions, so that two backends can share a store (both as proposed, with the timeout rule and the note on cached failures).

**Choices made here, not by the user** (each easy to change): the defaults in the table (placeholders, as the pool's are); no default directory for `FileStore` (a library shouldn't pick one; `stepconv` in phase 4 can); caching as a wrapper rather than a `tessellateScene` option; a worker's exit or failure mid-request not cached; running out of memory cached like any trap; deleting other versions on by default.

## Step 5: OCCT loose ends

**Parts without meshes, classified.** All 151 brep parts of the corpus files up to 5 MB that our OCCT backend gives no triangles (1,171 parts in all; scratch scan, every part through `tess-occt`), by what their representations hold:

| What | Parts | Representations | Now |
|---|---|---|---|
| Curves and points only | 136 | 66 `GEOMETRICALLY_BOUNDED_WIREFRAME`, 62 `GEOMETRICALLY_BOUNDED_SURFACE` (a `GEOMETRIC_SET` of trimmed curves and points, no surface), 4 `EDGE_BASED_WIREFRAME`, 2 `MANIFOLD_SURFACE` holding only a `GEOMETRIC_CURVE_SET`, 1 plain (`trj7_c2-sd-214.stp` #780, a curve set with annotations) | `curves` parts, step 6 |
| 2D drawings | 4 | `GEOMETRICALLY_BOUNDED_2D_WIREFRAME` (`trj2_d2-db-214.stp` and three others) | step 6 decides |
| Annotations only | 11 | plain `SHAPE_REPRESENTATION`s of text (`TEXT_LITERAL`, `COMPOSITE_TEXT`) and callouts (`LEADER_DIRECTED_CALLOUT`) beside placements, OCCT "no shape" | no longer parts (below) |
| A broken file | 1 | `bug31292.stp` #62, OCCT's deliberately broken references | stays an error |

So phase 2's "62 geometrically bounded surface representations our backend returns no shape for" were wireframes all along: the 16 that do hold surfaces (`CURVE_BOUNDED_SURFACE`s, B-spline surfaces, one `SHELL_BASED_SURFACE_MODEL`) were already meshed. And the 16 "no shape" errors were the 11 annotations, the 4 drawings and the broken file.

**Annotation-only representations aren't parts** (`step-import`): a representation is a part only if it holds an item other than placements, mapped items and annotations (instances of `TEXT_LITERAL`, `COMPOSITE_TEXT`, `DRAUGHTING_CALLOUT` or `ANNOTATION_OCCURRENCE`). In the 11 files the product's own representation was the annotation, with the geometry in representations related to it; each file loses that one part and instance and keeps every other (checked part by part). Presentation (graphical PMI) stays in the backlog.

**A geometric set's surfaces are faces.** Phase 2's end-to-end check showed every colour sample wrong in ten files with geometric sets (eight geometrically bounded surface representations, such as `trj8_c2-ac-214.stp` and `trj4_k1_geo-ac-214.stp`, and two plain shape representations, `trj7_c2-al-214.stp` and `trj7_c2-db-214.stp`), and some wrong in `trj3_s1-al-214.stp`: the styles are on the `CURVE_BOUNDED_SURFACE`s (or the `GEOMETRIC_SET`s), which the importer didn't treat as faces, and OCCT's faces made from them had no STEP id. Now:

- `tess-occt` gives each face made from a geometric set's surface that surface's id (OCCT binds each element's shape to it, `StepToTopoDS_Builder`, after the faces, so a face entity's id wins);
- `step-import` treats the surfaces among a `GEOMETRIC_SET`'s elements as the part's faces, so their styles (their own, or the set's) resolve as face styles do.

Nine of the ten now match OCCT's colours, and `trj3_s1-al-214.stp` went from 9 to 6 of 246 samples differing. In the tenth, `trj4_k1_geo-tu-214.stp`, the styles are on the 44 `GEOMETRIC_SET`s, all green; `occt-import-js` shows no colour at all, so OCCT drops them, and ours follow the file. `tr8_ha1_ug.stp` now differs in 4 of 28 samples, the other way: its square's only style is a `SURFACE_STYLE_BOUNDARY` (cyan) on a curve-bounded surface, which faces now show (the user's phase 2 decision on boundary colours), and `occt-import-js` doesn't. truck's wrapper builds shells only, so it still meshes no geometric sets (it reports them); meshing their surfaces with truck would be new wrapper work, not planned.

**OCCT 8 reads a lone boundary on a sphere or torus as a hole.** In `trj4_k1_geo-pe-203.stp`, `-pe-214.stp` and `-tu-214.stp` our meshes were 9–17% larger than OCCT's reading of the same files and than the other writers' copies of the model (`-tc-214.stp` 5,838 mm², `-md-203.stp` 5,756 mm²; the `-ac-214.stp` copy is a different part). Six (pe) and two (tu) curve-bounded spheres and tori were the complement of OCCT's: the two areas add up to the whole surface. `occt-import-js` is OCCT 7.6.1 (its submodule, `d2abb6d8`); in 7.6.1, `ShapeFix_Face::FixOrientation` reverses a face's lone wire when it doesn't classify as the outer bound, while 8.1 (`isNeedAddNaturalBound`) keeps it, on a doubly closed surface with no seam or degenerate edge, and adds the natural bounds, making it a hole. With `FixAddNaturalBoundMode` off, 5 of the 1,171 parts change: these three, and a face in each of two of OCCT's own bug files, `bug28414_bug_toroidal_surface.stp` (3,586 → 156 mm²) and `bug29564.stp` (5,826 → 6,216 mm²), whose OCCT tests expect 3,593.35 and 5,831.82: there OCCT 8 is right, and 7.6.1 is wrong (`occt-import-js` reads 156.3 for the first). Both of those are `ADVANCED_FACE`s, whose loops are topology; the three are curve-bounded surfaces in geometric sets. **So `tess-occt` turns the natural-bound fix off for geometrically bounded surface representations only.** The three now read 5,855, 5,855 and 5,779 mm² (OCCT 7.6.1: 5,853, 5,853, 5,774), and nothing else in the corpus changes. The files' wires, as OCCT classifies them, say the large region; the copies of the same CAx-IF test model written by other CAD systems say the small one. A reference from a third system confirms the small region: the user exported `-pe-203.stp` from Onshape to glTF (`trj4_k1_geo-pe-203.glb`, Draco-compressed, not committed), and each of its 52 surface bodies matched one of our 52 faces by centroid (0.00 mm apart). The six spheres and tori read 48.50, 48.50, 109.22, 48.96, 48.96 and 109.22 mm² in Onshape, 48.46, 48.46, 109.26, 48.98, 48.98 and 109.26 in ours, and 141.78–274.67 (150–1052% larger) with OCCT 8's natural bounds. The other 46 faces agree in all three within 0.34%, and the totals are 5,857 (Onshape), 5,855 (ours) and 6,822 mm². The workaround applies only when the request's root is the GBSSR. A whole-file request (no `rootId`) still gets OCCT 8's reading, but the tessellator API is meant for parts, as the importer sends them, so this doesn't matter (the user, 2026-10-19).
