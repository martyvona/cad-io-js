# Tessellation backends notes

Notes for work on `cad-scene`'s tessellation, `tess-occt`, `tess-truck`, `tess-smlib`, `tess-workers` and `tess-cache`. The full record (measurements, alternatives, checks) is in `git show V0.2.0:CLAUDE.md`; phase 0's backend comparison and spike in `V0.1.0`'s.

## Phase 0

The per-part interface: requests carry the part's B-rep model (`cad-brep`; `brep-model.md`), which OCCT builds itself by default (its native route) and `step-export`'s `StepTessellator` writes as a bare STEP file (its shape representation, with the source's `#` ids) for backends that read STEP (truck, OCCT's STEP route), after the cache, reading the ids in their results back as the model's (the writer's own for entities without a source id none: `brep-model.md`, decision 23); faces may repeat an id or have none; units are file units; the host owns recycling and the watchdog; edges come with kinds and dihedral angles. Bare representations are faster and more robust than whole files. OCCT 8.1 (our build) is the primary backend (bare subsets need product mode off; face ids from transfer bindings), truck optional (much smaller and faster, less robust); `occt-import-js` (no face ids, no bare subsets) and monstertruck not adopted. A "load once, tessellate many" session API was rejected.

## The host side

- Backends take a host's module through `init` (`glue`, `wasm`, `version`; a compiled module needs `version`). `info.version` carries the module's hash, so caches see each build. Custom OCCT builds must link our wrapper (`occt_tess.cpp`).
- `tessellateScene` adds its meshes to the parts' levels (`from: 'tessellated'`, deflections in mm and radians, `backend` name and version), replacing one from the same backend and settings (equal to 1e-9 relative), mutating the scene; returns diagnostics and the meshes made. It turns over closed shells that are inside out and enclosed by nothing, drops triangles with two corners at one position, boxes each mesh (`Mesh.box`), and with `outlines` outlines failed faces from the file. Vertices aren't merged.
- Meshing profiles (`cad-scene`'s `profiles.ts`, the one place they're defined): coarse 0.2 mm / 30 degrees, medium 0.1 mm / 15 degrees (`DEFAULT_MESH_PROFILE`), fine 0.05 mm / 7.5 degrees; `linearDeflection` and `angularDeflection` override. The corpus checks name a profile: coarse for those that only consume meshes (`export_view`, `gltf_corpus`, `threejs_corpus`, `threemf_corpus`, `weld_survey`, `roundtrip_corpus`), medium, as users get it, for those of meshing itself (`area_occt`, `step_route`, `backend_speed`; `stepconv_corpus` through `stepconv`'s default); `scene_occt` (a deflection relative to the model's size on both sides, to match `occt-import-js`) and `truck_occt` (0.05 mm) keep their own.
- Timeouts: 120 s by default (`DEFAULT_TIMEOUT_MS`, `stepconv`, the pool, the viewer). The corpus's slowest successful part, `bug24024_slow_import.stp`'s largest, takes about 61 s with OCCT at 0.1 mm with measures on an M4 (28 s without measures when first measured); slower machines or finer settings may time it out. Workers: cores - 1.
- Caching: maximum size (0 disables), failures and timeouts cached (a cached timeout answers only while the limit is no longer), only the same backend's other versions deleted, a wrapper rather than a `tessellateScene` option; a worker's exit not cached, out-of-memory traps cached. Edges and measures aren't in the key (a backend's triangles don't depend on them: each backend's tests check it); an entry records whether its request asked for them, and answers a request asking for no more (edges taken off when not asked for), else the part is meshed again and the entry replaced; a request that asked for measures and got none (a part without faces, truck) still answers, so such parts aren't meshed again on every request. Keys start with the format's tag (`F4_`; earlier formats' keys are lower case): a store holding any key without it is cleared on first use, in every store, files and IndexedDB alike.
- Defaults: `maxMemoryBytes` 256 MiB (recycle above it; a restart costs about 250 ms), caches 256 MiB memory and IndexedDB, 1 GiB files.
- Wireframe curves and points come in the B-rep result, OCCT only; 2D drawings skipped.
- SHA-256 everywhere (`cad-scene`'s `sha256`: Web Crypto where it exists, our `sha256Js` where it doesn't, since `crypto.subtle` is missing outside secure contexts, e.g. a page over plain http, not from localhost).

## Threads and SharedArrayBuffer (not used)

The backends are single-threaded modules, one per worker in a `tess-workers` pool (cores - 1), the pool giving the parallelism. Threads inside a module (Emscripten pthreads, threaded Rust) and `SharedArrayBuffer` need a cross-origin isolated page (COOP `same-origin` and COEP `require-corp` or `credentialless`). GitHub Pages can't set headers, but a service worker can add them to every response it answers (https://github.com/gzuidhof/coi-serviceworker; the page reloads once when the worker first controls it), and the viewer already has one, so it is tractable when a backend needs it. The limits and costs:

- **One worker, ours:** a scope has one controlling service worker, so the headers go into ours (Workbox's, from `vite-plugin-pwa`), coi-serviceworker's rewrite taken into it rather than its script added; precached responses need them too, as they leave the cache.
- **Isolation before anything runs (decided, for when threads come):** threaded modules only; the alternative, a single-threaded build beside each for pages that can't be isolated, rejected. In the viewer a small script in `index.html` runs before any module loads: it registers the worker, waits for it to control the page and reloads once (the first visit, or after the worker was unregistered or its storage cleared), and lets the app start only when `crossOriginIsolated` is true. A hard reload (it bypasses the worker) finds the worker registered but not controlling: one plain `location.reload()` goes through it. A counter in `sessionStorage` stops after one or two tries, since where the worker can never control the page that would loop: no service worker at all (some private-browsing modes, historically Firefox's, unchecked; site data blocked by the user or a policy), an iframe in a page that isn't isolated itself, our build on a server without the worker's scope or on plain http. There the viewer says why it can't run ("open it in a normal window"), rather than falling back. A host that sends the headers itself (Netlify's or Cloudflare Pages' `_headers`, or a proxy in front of Pages; not GitHub Pages, and not a `<meta>` tag, which browsers ignore for COOP and COEP) isolates the first byte and makes the reloads unneeded; the worker then stays for offline use only.
- **The packages in other apps' pages:** cross-origin isolation documented as a requirement of the threaded modules (the host page's choice); single-threaded builds published only if someone needs them. Node needs nothing (`SharedArrayBuffer` and worker threads always exist).
- **COEP blocks other origins' subresources** fetched without CORS unless they send CORP (under `require-corp`; `credentialless` relaxes it where supported, Safari unchecked). `fetch` is CORS, so Load URL... and `?model=` are unaffected; anything else from other origins would need checking.
- **What it would buy:** with the pool, mostly not throughput: one large part's latency where the mesher itself is parallel (BRepMesh per face; SMLib's tessellator's `parallel_for`), one module's memory instead of one per worker (phones), and meshes shared between workers without copying. Against: larger, slower-starting threaded builds, Emscripten pthreads' rough edges, an extra reload on a first visit and after a hard reload, and no viewer where isolation is impossible.
- **First step when needed:** the headers and the start script in our worker and page on a branch, deployed to Pages; `crossOriginIsolated` checked on desktop Chrome, Firefox and Safari, iOS and Android, after a first visit and after a hard reload, and the guard's message in a private window, before any threaded build.

## Faces that fail to mesh

- `Part.measures` (`by`, and `faces` by source id: `area`, `perimeter`, `valid`), measured by OCCT in the tessellation call when asked (`occt_set_measures`: per STEP face its healed pieces' `BRepGProp` area and length, `valid` when `BRepCheck_Analyzer` passes every piece; about 3 % of meshing time) and carried in our extras through exports.
- `faceFailures` (`cad-scene`'s `mesh.ts`) gives `failed` (no triangles, area over d x d), `partly` (mesh area short by more than max(3 % of A, d x P)), `excess` (over by more than max(10 % of A, d x P)), `unverified` (no valid area, or over 1e20); d the linear deflection, P the perimeter (`MISSING_FRACTION`, `EXCESS_FRACTION`, `BOUNDARY_SLACK`, `MAX_PLAUSIBLE_AREA`). Without measures or a known deflection, only the no-triangles rule. A face several shells use (AP209's solids sharing faces) is meshed once in each under its one id, so its triangles are judged against its measures times its uses (`FaceMeasures.uses`, from the model's face uses, kept in our extras). All but `partly` draw red in the viewer.
- Why areas: OCCT can mesh a face only in part with no empty piece (VW's Differential Pinion), and healed pieces' areas can be wrong by half (Ring Gear #297982). Valid faces' areas can be wrong too: against the area oracle (below) 184 of 63,665 analytic faces are more than 1 % off, all valid by BRepCheck, among them a sphere face meshed and measured as its complement (`trj3_s1-ct-203.stp` #1939: 34,450 mm^2 for 10,789). 621 corpus faces measure under 0.01 mm^2, but `bug30790.step`'s 148 at 1e-17 mm^2 are not empty: each bounds a whole closed B-spline tube of 0.98674 mm^2 (the surface integrated independently) with two 0.2 mm circles, and OCCT's healing collapses them (its perimeter is one circle); they are OCCT failures that `faceFailures` can't see, since the measure agrees with the empty mesh. `bug30790.step` parts 11-24 mesh 616 mm^2 faces to 12,900 mm^2: garbage meshes (`excess`).
- Failed faces' red outlines: the backend's polylines for a wholly failed face, else the source's outline.

## The area oracle

An area for a STEP face from the file alone, independent of OCCT, truck and every other kernel: `corpus_checks/area_oracle.ts` (`AreaOracle`, `trusted`, `planeAngleUnit`; it reads the file through `step-parser` alone, and takes a parsed file or a part's subset; `modelFaceArea` is the same oracle on a face of the B-rep model, sharing only the integral, its geometry through `cad-brep`, so the two checked against each other check the model's conversion: `brep-model.md`, phase 3), tested by `test/area_oracle.test.ts` (faces built with closed-form areas; every planted bug caught but one equivalent), and run against our OCCT backend by `corpus_checks/area_occt.ts`.

- **Method:** Green's theorem in the surface's own (u, v) parameters: area = oint P(v) du with dP/dv = -\|S_u x S_v\| (plane P = -(v - v0); cylinder -r v; cone -rho \|rho\| / (2 sin a), rho = r + v tan a; sphere -R^2 (sin v - 1); torus -r (R v + r sin v)). Each edge is sampled on its 3D curve between its vertices (the parameters of the vertices in closed form for conics, by nearest-point search for B-splines), each sample mapped to (u, v) in closed form, u unwrapped along the loop, the loop's sense from its `FACE_BOUND` and oriented edges, the face's from `same_sense`. Trapezoid sums at N, 2N and 4N samples (256 per turn of a conic, 64 per knot span of a B-spline, at least 16 per curved edge, at most 200,000), Richardson-extrapolated from 2N and 4N; `error` is the difference from the extrapolation from N and 2N, a bound in practice far above the real error. The perimeter (the loops' length) is extrapolated the same way. P is zero at a cone's apex and a sphere's north pole, so a loop through either (its u undefined there) needs no jump term; at a sphere's south pole the jump in u is ambiguous by 2 pi, which changes the sum by exactly 4 pi R^2, so sphere areas are reduced modulo the sphere's. On planes v is measured from the face's first vertex (a constant in P adds c oint du, zero on a plane), so small faces far from their plane's origin don't cancel.
- **Trusted** (`trusted`): no flags, and `error` within 1e-6 of the area. Flags: `orientation` (the loops' signed sum negative: loops against Part 42's orientation; the absolute value reported), `minor-winding` (a torus loop winding the minor circle: the face then spans a seam no loop runs along, which this method can't count), `no-loops`, `off-surface` (a loop's point farther from the surface than 1e-2 of the loops' size, `offSurface` in the result: an edge that isn't on the face, a file's topology error, as in `bug29979_firetherm_12.step`, whose faces #36207 and #195244 reach edges hundreds of millimetres away through nested `ORIENTED_EDGE`s).
- **Coverage over the corpus** (`area_occt.log`): of 82,989 faces, 63,899 trusted (77 %: 27,278 planes, 26,840 cylinders, 4,435 cones, 3,251 tori, 2,095 spheres), 499 untrusted (404 for their error estimate, 78 orientation, 8 minor winding of which 4 also orientation, 7 no loops, 2 off surface), 18,591 unsupported (16,342 B-spline surfaces, 1,938 extrusions and revolutions, 160 degenerate tori, 62 edges whose vertices run against their curve's sense, 42 faces reaching instances their part's subset lacks, 33 hyperbola and parabola edges, the rest odd forms).
- **What it doesn't handle (unsupported, with the reason):** surfaces other than `PLANE`, `CYLINDRICAL_SURFACE`, `CONICAL_SURFACE`, `SPHERICAL_SURFACE` and `TOROIDAL_SURFACE` (B-splines of every form, Bezier and quasi-uniform surfaces, extrusions, revolutions, offset, swept and trimmed surfaces, degenerate tori, horn and spindle tori, cones with a zero semi-angle); edge curves other than `LINE`, `CIRCLE`, `ELLIPSE`, `B_SPLINE_CURVE_WITH_KNOTS` (rational too, as a complex instance) and those reached through `SURFACE_CURVE`, `SEAM_CURVE`, `INTERSECTION_CURVE`, `BOUNDED_SURFACE_CURVE` (their 3D curve) or `TRIMMED_CURVE` (its basis, between the edge's vertices; the trim parameters are ignored): no hyperbolas, parabolas, polylines, composite, offset, Bezier, uniform or quasi-uniform curves, nor p-curves as edge geometry; face instances other than simple `ADVANCED_FACE` and `FACE_SURFACE` (complex instances, `ORIENTED_FACE`, `SUBFACE`); loops other than `EDGE_LOOP` and `VERTEX_LOOP` (a vertex loop counts nothing, right at an apex or pole, and a point anywhere); B-spline edges whose vertices run against the curve's sense.
- **Where a computed area can still be wrong** (no flag says so):
  - It trusts the file's 3D curves, vertices and surface, and ignores p-curves: a file whose 3D geometry is wrong gets that geometry's area. Edge points off the surface by less than `off-surface`'s threshold are moved onto it by the closed-form inverse; the error that makes is of order the offset times the perimeter and isn't in `error`.
  - It trusts Part 42's orientation for the face's side: reversed loops give `orientation` on most surfaces, but on a sphere the reduction modulo 4 pi R^2 turns them into the complement, unflagged; and a face covering a whole sphere reduces to 0 (normally such a face has no edge loops and is flagged `no-loops`).
  - Nearest-point search for a B-spline edge's vertex parameters can pick the wrong branch on a curve that comes back near itself; an edge's ends are one point (a closed edge) when they are the same vertex instance or within 1e-9 of the curve's size; a pole or apex when within 1e-9 of the axis relative to the radius.
  - The plane angle unit is the first geometric context's with global units in the file or subset, not each representation's own: a file mixing angle units across contexts would get some cones wrong. A degree unit used only for PMI doesn't count (an early version got cones wrong so).
  - Extrapolation assumes a smooth integrand along each edge; kinks (a vertex off its curve, a B-spline's tangent discontinuities) slow convergence, which shows as a larger `error` and so as untrusted, conservatively.
  - It checks an area and a perimeter, not a shape: a mesh of the wrong region with the right area agrees with it.
- **Units:** the file's (or subset's) length unit; the caller converts.
- **Cost:** sampling at three levels and, for B-spline edges, a dense nearest-point scan per vertex; untuned. The corpus check's oracle work is a small part of its time next to tessellation, but no budget was measured for runtime use.
- **What the check found** (`area_occt.log`): OCCT's measured area within 1e-4 of the oracle's on 97.0 % of compared faces, more than 1 % off on 184; failures the library can't see (OCCT's measure wrong with its mesh) on 6 faces, all spheres: one sphere face meshed and measured as its complement in five files (`trj3_s1-ct-203.stp` #1939, `trj3_s1-ct-214.stp` #1905, `trj5_s1-in-214.stp` #1095, `HEAD_BACK.stp` #314, and at a tenth the size `trj3_s1-db-214.stp` #3850), and `ec_turbine-A.stp` #11034 meshed at 654 mm^2 of 1,004; faces only OCCT's measures fail: 6 OCCT calls unverified (invalid by BRepCheck) whose meshes the oracle finds right, and `trj12_b3-tu-203.stp` #26838, OCCT's measure 4 % high. Plane perimeters agree with OCCT's within 1e-4 on 99.8 %; the 12 more than 1 % off weren't investigated.
- **Later:** B-spline faces (the file's edge points projected onto the surface by Newton, periods handled on closed surfaces, then the same line integral with P(u, v) = -int_{v0}^{v} \|S_u x S_v\| dt by Gauss-Legendre per knot span; a whole-surface integration settled `bug30790.step`'s tubes), and extrusions and revolutions (closed forms in their profile curves). And promotion into the runtime library, to cross-check a backend's meshes and measures as they're made (`faceFailures` with the oracle's area where it trusts one, as `area_occt.ts` does): the module is self-contained for that, but it would need a package, a cost budget per part, diagnostics rather than results for problems, and a rule for disagreements (which to believe, and what to draw).

## OCCT

- **Build:** `-UOCC_CONVERT_SIGNALS` or the full link is invalid WebAssembly (V8 `br_table: label arity inconsistent`: LLVM's `setjmp`/`longjmp` lowering of `OCC_CATCH_SIGNALS`, a wasm-ld bug); set `CMAKE_CXX_FLAGS_RELEASE`, or OCCT appends `-O3` after your flags; `-O2`/`-O3` are no faster than `-Os` and larger, LTO larger with no gain. The data segment is mostly TKernel's CJK code-page tables and `AdvApp2Var` tables. We build `-Os` without the `VBernstein` patch.
- **Our patches** (`occt_patches/`, unified diffs applied by `build-occt.sh` to the worktree `build/occt-src/`, reset each run; a patch that doesn't apply stops the build; each with a header giving bug, evidence and check, and named in the backend's version). Not reported upstream.
- **Bare subsets** need `read.step.product.mode` off: `NbRootsForTransfer` takes an unshared `SHAPE_REPRESENTATION` as a root only then.
- **Units:** compute the root's length unit (`STEPConstruct_UnitContext::ComputeFactors`) and pass it to `SetSystemLengthUnit`, so output is in file units.
- **Face ids:** `TransferBRep::ShapeResult(TP, entity)` for every `StepShape_FaceSurface` gives the faces after shape fixing (ShapeFix splits faces, so an id can repeat). Geometric sets' surfaces likewise (a face entity's id wins). Edge ids from `StepShape_EdgeCurve`; curve ids from the set's element, a `COMPOSITE_CURVE` before its segments' curves.
- **Edges:** `TopExp::MapShapesAndUniqueAncestors(shape, EDGE, FACE)`, each edge's `Poly_PolygonOnTriangulation` on its first face, else its `Polygon3D`, else its vertex; dihedral angles from the faces' mesh normals (OCCT's stored continuity isn't computed on import). Unmapped edges are OCCT's own (poles, seams added to periodic faces).
- **Messages** go through Emscripten's `print`; collected per call so they can't reach `stepconv -o -`'s output; kept per part as warnings (at most 10, 1000 characters). "Unresolved Reference" can be triggered by the header alone.
- **OCCT 8.1 against 7.6.1** (`occt-import-js`): 8.1's `ShapeFix_Face` adds natural bounds to a lone wire on a doubly closed surface, right for `ADVANCED_FACE`s (`bug28414_bug_toroidal_surface.stp`, `bug29564.stp`) but wrong for curve-bounded spheres and tori in geometric sets (`trj4_k1_geo-pe-203.stp`), so we turn it off for geometrically bounded surfaces only. `occt-import-js` is itself wrong on some parts (bicycle #1170) and drops faces' fill colours in `2.stp`.
- **ShapeFix at a seam:** a hole whose vertices lie on a closed B-spline's seam (bicycle #23723) projects open by one period; `FixMissingSeam` and `ShapeFix_ComposeShell` then make an overlapping face and a zero-area one, slowly. No ShapeFix mode helps. Left as is.
- **BRepMesh's cone seam amplifier** (patch `0001`, `conical-surface.step`): `SeamEdgeAmplifier` matches pcurves by the point at `FirstParameter()`, -2e100 for a `Geom2d_Line`, so a seam line with any U slope swaps them and the face fails. Found with a probe build running the mesher's stages one at a time through `BRepMesh_Context` (initialise parameters as `BRepMesh_IncrementalMesh::initParameters` does, or the healer crashes on `MinSize` 0). Lesson: an expectation that encodes a difference without finding its cause (truck's "1.35 x OCCT's area" there) can hide the other side's bug.
- **Tessellated strips and fans:** OCCT 8.1 (`StepToTopoDS_TranslateFace`) winds them the reverse of Part 42 (the files' normals agree with Part 42), gives no face ids and no edges; we read them ourselves.
- **Placements without a reference direction:** OCCT's STEP reader completes them with `gp_Ax2(P, N)`'s own choice of x, not Part 42's `build_axes` (`StepToGeom.cxx`); the x direction, and so a surface's u, can be the opposite of the standard's (`bug27693_cornetta-step.stp`'s plane #1559). Where p-curves or trim parameters lie on such a placement OCCT reads them against the wrong x. From the B-rep model OCCT gets Part 42's x written out (`brep-model.md`, phase 4).
- **`ORIENTED_FACE` not read:** OCCT's shell translation takes only `FACE_SURFACE`s (`ADVANCED_FACE`s among them), so a face a shell or face set uses through an `ORIENTED_FACE` is left out ("Face is not of FaceSurface Type; not mapped to TopoDS"); a face set of nothing else gives no shape. Our writer therefore writes a face used reversed turned over instead (`brep-model.md`, decision 19).
- **Faces against their closed shell:** shape healing turns a face whose sense disagrees with its closed shell back, so OCCT's meshes can't show a face's sense there (`step_route.ts`'s planted senses: 3 of 39 seen).
- **Last bits:** BRepMesh's triangulation, and BRepGProp's areas of faces off their surfaces, change with directions' last bits (normalized again, x made orthogonal to the axis): from the B-rep model, which keeps them so, about one face in a thousand gets other triangles, and OCCT's areas of faces off their surfaces move by a few 1e-6 (`brep-model.md`, phase 4).
- **Slow parts:** by size at an absolute deflection (`bug28366_fuselage.stp` #368, `as1_motor.step` #6322), or faces with thousands of holes (`bug24024_slow_import.stp` #76247; Delabella faster there but leaves more faces untriangulated over the corpus). `bug30790.step`'s parts #11-21 and #24 get far slower at tighter angles (0.5 s at 28.6 degrees, 24-44 s at 15, timeouts at 12.5): not investigated; a probe timing BRepMesh's stages would show where.
- **Memory:** linear memory never shrinks, but is reused, so the heap grows only to the largest part so far.
- **`instantiateWasm`:** this Emscripten build ignores `Module.wasmBinary`; hand it the compiled module through the hook (needed to hash the module).
- **The `VBernstein` patch** (`occt_overlay/`, unused): computes the 840 kB Bernstein table instead of storing it (-468 kB brotli); reached only by `AppCont_LeastSquare`, never by the corpus. If adopted, check the upstream header's hash in the build.
- **The probe** (`native/occt_probe.cpp`, `build-probe.sh` -> `dist/occt_probe.mjs`, for checks, never the library): OCCT's points on a bare representation's faces and edges at given parameters, by STEP id, read without shape processing (`SetShapeProcessFlags` with no operations), curve items' edges among the edges; or (`occt_probe_build`) a part's model built by the native builder, unhealed, by source ids. Used by `corpus_checks/step_roundtrip.ts` (two files' readings) and `corpus_checks/native_route.ts` (the two routes' shapes; `brep-model.md`, phases 6 and 7).
- **The native route** (the default, `OcctTessellator()`; `route: 'step'` the STEP route, kept as its oracle; `native/occt_build.cpp`, `brep-model.md` phase 7 and decision 8): a part's model built into OCCT's shapes through its API, then the STEP reader's default shape processing and the same meshing. Healing's result depends on how the shapes were built, so the builder matches what OCCT's STEP translator hands healing (decision 15), each point found by comparing the routes over the corpus: shapes built at 1e-7 with the part's uncertainty as healing's `Tolerance3d` (built at the uncertainty, healing splits a ring on a closed B-spline into two empty faces); `MaxTolerance3d` as the reader sets it; loops' wires marked closed; B-spline data as the reader takes it, a B-spline face's surface in periodic form where closed (`ConvertToPeriodic`; without it, 1,036 corpus faces between two circles meshed empty); a surface made for each face, not shared by faces on one surface (a p-curve is kept per edge and surface, so a hole's two halves on one cylinder clash over their shared edges' p-curves and healing turns one into the rest of the cylinder: 253 faces). Faces at a sphere's pole, where healing adds an edge, differ by about 1e-6 of their area between the routes (last bits of the text, u undefined at the pole). Edges, loops and p-curves are made as the translator makes them (`brep-model.md`, phase 7 step (b)); faces several solids share (AP209's) keep their ids on the native route, where the STEP route's healing copies them without. A closed edge on a periodic B-spline curve ranged from its vertex's projection alone once ran out of bounds in OCCT (`Geom_BSplineCurve::Segment`, `bug32049_sp7_10nx_242.stp`); ranged as the translator ranges it, not, the cause not found.
- **A 2D offset p-curve crashes the STEP route:** OCCT's reader of our written STEP fails inside the module ("null function or function signature mismatch") on an `OFFSET_CURVE_2D` as a p-curve; the native route builds the same model. No corpus file has one.
- **`-DNo_Exception`:** OCCT's release libraries are built with it (`BUILD_RELEASE_DISABLE_EXCEPTIONS`), which compiles out its headers' inline checks (`Standard_*_Raise_if`: a zero `gp_Dir2d`, an index out of range); our wrapper is built with it too, so those checks behave in our code as in OCCT's (a zero direction from coincident points isn't an exception there either) and the linker never picks between two differing copies of an inline function.
- **Probing:** copy `occt_tess.cpp` to the scratchpad, add probes switched by environment variables (through `Module.ENV` in `preRun`; Node's `process.env` isn't seen), link against `build/occt-Os` (compile 1 s, link 7 s). A probe's `printf` reaches the adapter's messages, not the terminal. Healing changes shapes in place, edges shared included: dump a shape as built before shape processing runs, or it shows healing's p-curves.

## truck

- **Workarounds** in `native/src/lib.rs` (truck unchanged): (1) shells built by the wrapper, so ids survive faces and edges that fail; (2) `AXIS2_PLACEMENT_3D` without `ref_direction` on an +/-x axis gets (0, 1, 0) per Part 42; (3) shells reversed by volume sign; (4) `SURFACE_CURVE`s by their 3D curve; (5) NaN edges and faces left out (truck subdivides NaN curves until memory runs out); (6) instances truck's parser can't read skipped one at a time (ruststep fails the whole file on `()`); (7) negative torus radii as absolute; (8) cone semi-angles from the context's angle unit; (9) a shell reversed only if its mesh is consistently oriented; (10) unclamped B-splines clamped; (11) a face meshed against all its loops reversed; (12) the volume sign trusted only if the same from every point of the bounding box and at least 1 % of the sum of the triangles' contributions.
- The tolerance is the linear deflection; the angle is ignored.
- **What's left:** cones near the apex, surfaces of revolution, rational B-splines; timeouts in NURBS evaluation (9 corpus hangs that never finish); empty parts (geometric sets, triangulated faces, unsupported surfaces). About 83 % of parts complete and on OCCT's geometry. A truck fallback for OCCT's failures isn't shown to be safe.
- Comparing orientation or area with OCCT measures OCCT's healing as much as truck: compare geometry (sampled vertices on the other's faces) and the file's own loops.
- **Size and speed:** opt-level 3 (`s`, `z` save little at 1.5-3.5 x the time). On parts both mesh, truck 2.2 x faster in total, 26 % fewer triangles; its hangs make whole runs far slower. Five wasm-bindgen imports from chrono and getrandom are stubbed; a test pins the import list. `info.license` is AGPL-3.0-only (our wrapper over truck's Apache-2.0).
- **monstertruck** fixes some parts and regresses others, with 9 x the triangles; not adopted.

## BRL-CAD (evaluated, not pursued)

A possible third backend, reviewed 2026-11-07 at `ace9ae6ef4` (2026-11-06; https://github.com/BRL-CAD/brlcad, a sparse clone, not in `third_party/`), for the status quo: a STEP subset in, triangles per face out. **Not pursued** (the user, after the native spike below): over the corpus it meshes about 166 of OCCT's 182 failed faces, but loses 18 % of faces in conversion, gets more than 1,100 analytic faces' geometry wrong, and its fast mesher doesn't honour the requested tolerance, so it would fix far fewer faces than it breaks.

- **The pieces it would take:** STEP is read by an application, not a library: `src/conv/step/step-g` (`STEPWrapper` and a C++ class per entity, `AdvancedFace.cpp`, ..., converting to openNURBS `ON_Brep`s, with repairs of its own: seams, loops, periodic surfaces, p-curve pullback; schemas for AP203, AP214 and AP242 up to edition 4), on STEPcode (its own fork, generated C++ per schema) and writing a BRL-CAD `.g` database through `libwdb`, which a backend would replace with its own output. The mesher is `libbrep`'s CDT (`src/libbrep/cdt/`, about 48 k lines, maintained: 100 commits since 2020, 6 since October 2026): `ON_Brep_CDT_Create`/`_Tessellate`/`_Mesh` (watertight, with repair tiers, failed-face reports, a time limit per face) and `brep_cdt_fast_ex` (display quality, with a per-face callback giving each face's output ranges, so face ids survive; limits on time, memory, points). `libbrep` needs `libbv`, `libbg`, `libbn` and `libbu` (BRL-CAD's portability, geometry and numerics libraries), openNURBS and Geometric Tools (GTE), from BRL-CAD's external-dependency tree (`bext`).
- **So no clean subsystem** compiles alone: a WebAssembly build means porting `libbu` (files, threads: Emscripten pthreads need cross-origin isolation, which our service worker could give, below), STEPcode with generated schemas (likely the bulk of the module's size; unmeasured), `step-g`'s reader without its `.g` writer, and `libbrep` with its dependencies. Feasible, a project the size of our OCCT build or larger.
- **With the neutral B-rep model instead** (`brep-model.md`; `future.md`, "Across formats"): `step-g` and STEPcode drop out; the backend is our wrapper building `ON_Brep`s from the model's arrays, then the CDT, on `libbrep`, openNURBS and BRL-CAD's base libraries (a far smaller module; unmeasured). openNURBS's vocabulary is narrower than the model's, so the wrapper converts as `step-g` does (`OpenNurbsPrimitives.cpp`): planes as bounded `ON_PlaneSurface`s; cylinders, cones, spheres and tori as bounded `ON_RevSurface`s (a cylinder built twice the model's bounding diagonal long; `ON_Torus` rejects horn and spindle tori, so those as a revolved rational circle); extrusions as `ON_SumSurface`; B-splines as `ON_NurbsSurface`s (openNURBS's knot vectors leave out the end knots); ellipses, hyperbolas and parabolas as rational NURBS; offset curves as adaptive polylines within the model's tolerance and offset surfaces by sampled profiles (approximations, with the self-intersection risks of offsets). Every face needs trims (p-curves in the openNURBS surface's own parameterization, which for revolved surfaces differs from STEP's), so the model's p-curves are remapped where the parameterizations correspond affinely, else pulled back (`libbrep`'s `PullbackCurve`, as `step-g` does). Tolerances per edge, vertex and trim exist in `ON_Brep`. Face ids are the model's face indices, reported back per face (`face_output`). Its fast mesher can take the boundary samples from the host (`trim_sample` callbacks: trim parameter, UV, exact 3D point), so a host could give two backends the same edge discretization and mix their faces without cracks: a per-face fallback between OCCT and BRL-CAD, if OCCT's mesher can be held to given edge polygons too (unchecked). The conversion code can be taken from `step-g` into the wrapper (both LGPL-2.1).
- **Native spike over the corpus** (`workdir/2026-11-07_brlcad/README.md`, ignored; `ace9ae6` with step-g patched to keep STEP face ids in `m_face_uuid`): per STEP face, OCCT, truck, step-g with libbrep's rigorous CDT and fast CDT at 0.1 mm / 0.5 rad, and areas from an oracle independent of all of them (Green's theorem in the surface parameters from the file's own curves, for planes, cylinders, cones, spheres, tori: 50,304 of 82,955 faces; within 1e-4 of OCCT's `BRepGProp` on 98 %). BRL-CAD has no exact B-rep area of its own; the probe computes one on step-g's B-rep (Green's theorem over the trims with Gauss quadrature).
  - **step-g:** 15,235 faces (18 %) never reach a B-rep (22 of 466 files convert nothing: import failures, STEPcode segfaults and an abort, a 20 min timeout; pre-standard AP214 `AUTOMOTIVE_DESIGN_CC*` schema names rejected outright). Its B-rep's area is more than 1 % off the oracle on 1,166 analytic faces (mostly cylinders, spheres, cones, tori as `ON_RevSurface`s), against OCCT's 101, and its own mesh follows the wrong area: conversion errors. Loop types and directions are unreliable (bounding loops typed inner).
  - **Rigorous CDT:** all or nothing per B-rep; 409 of 3,877 objects meshed, 2,658 refused as not closed oriented manifolds.
  - **Fast CDT:** no crashes or hangs; 54,675 faces within area, 4,651 short, 1,885 empty (1,836 in `bug24024_slow_import.stp`), 1,061 over; 4,801 of the short and over have the face's whole boundary and no holes but an interior off the surface, reported as completed (the requested tolerance not honoured).
  - **On OCCT's 182 failed faces:** the fast CDT meshes 166 (`bug30790.step`'s 148 tubes at 0.963 mm^2 of 0.98674; one garbage, `bug25166_piston.stp` #10183 at 1.66e8 mm^2), 17 never reach a B-rep; the rigorous CDT none. On OCCT's 15 partial or excess faces the fast CDT is right on 12.
  - **Balance on this corpus:** it meshes a few hundred faces OCCT fails, and loses or misshapes several thousand OCCT meshes correctly; and conversion dominates its time (step-g 11,838 s summed over the corpus, the fast CDT 368 s; not a benchmark).
- **What would reopen it:** the neutral-B-rep route (above), which skips step-g and STEPcode and so its conversion losses and revolved-surface errors, with the fast CDT holding the requested tolerance; then as a per-face fallback for faces OCCT fails, given the same edge discretization (`trim_sample`). A smaller project than a STEP backend, but untried: re-run the spike's comparison on its output first.
- **License:** BRL-CAD as a whole is LGPL-2.1 (`COPYING`; the files say "version 2.1 as published", so 2.1 only); libraries and applications alike, with BSD or public-domain build files and data and BSD documentation (BDL). Its `COPYING` excludes third-party code under the GPL; the third-party code `libbrep` and `libbg` embed is MIT, ISC, Boost or public domain (`doc/legal/embedded/`), and openNURBS, STEPcode and GTE are MIT-style, BSD-3 and Boost. No GPL part was found in what a backend would use. **Compatibility:** as `tess-occt` is, a separate package under LGPL-2.1 (our wrapper with it), loaded by a host through `init` as a replaceable module: LGPL-2.1 lets AGPL-3.0 code use it so, on LGPL terms for the module (its source, and replacing it). LGPL-2.1 section 3 also lets a copy be relicensed to the GPL, version 2 or a later one, and GPL-3.0 code may be combined with AGPL-3.0 (its section 13), so even merging it into an AGPL package would be allowed (not legal advice).

## SMLib (`tess-smlib`)

SMLib is Solid Modeling Solutions' kernel on Piegl and Tiller's NLib, published by NVIDIA in USD BRep (https://github.com/NVIDIA-Omniverse/usd-brep, 1.0.1, `3fd5b95`, Apache-2.0; `third_party/usd-brep`): about 970 k lines of C++ plus its `SM_API` layer, with booleans, fillets, sweeps, offsets, a healer, exact mass properties and a tessellator, and no STEP or IGES reader. Its `.agents/` notes (`skills/smlib-brep-model/references/brep-format.md` above all) document its B-rep model. Evaluated 2026-11-07, built 2026-11-11 (`workdir/2026-11-11_smlib_backend/`: the plan, probes, runs), its failures classified and worked around 2026-11-12 (`workdir/2026-11-11_smlib_failures/`: per-face dumps, tallies, probes; both ignored).

- **Build:** `build-smlib.sh` compiles SMLib and SM_API (235 files) into one static library, for Emscripten (`-Os -fwasm-exceptions`, about 80 s on 4 jobs) or natively (`T=native`, for probes); oneTBB, its only dependency (a few `parallel_for`s, `task_arena`, the scalable allocator), replaced by a serial stand-in (`native/tbb/`). Each library's `inc/` must come first for its own files: both have a `StdAfx.h`, and SM_API's declares more. The module is 3.2 MB (OCCT's 7.3 MB).
- **The builder** (`native/smlib_build.cpp`) fills SMLib's flattened B-rep tables (`SmBrepData`) and calls `SmBrep::MakeTopologyFromData`, which links the topology, makes each coedge's (u, v) trim from its 3D edge and the surface, and heals (healer version below `SM_HEALER_VERSION` asks for it). One SMLib B-rep per shell, face item, natural-bounds face or loose surface, each shell in SMLib's open-sheet form: one region (the infinite one) holding one shell with both faceuses of every face, which takes faces whatever their orientation. Radial rings alternate orientation from a use along the edge (`m_lNextEU`, `m_lMateNextEU`: i for a record's first edgeuse, -i-1 for its mate). Face rows ride as user index 1, edge rows as an `SM_AI_EDGE_ID` long attribute (row + 1) x 4 + kind.
- **Parameters aren't passed.** SMLib's analytic surfaces have a "STEP" (u, v) (Part 42's, angles in degrees) and a NURBS (u, v) faces' domains are in; the builder builds each surface from the model's placement and radii, computes the face's box in Part 42's (u, v) from its boundary in closed form, hands it to `AdjustSTEPUVDomain` and takes the face domain from `ConvertDomainFromSTEPToNURBS`. A periodic direction spans a whole turn from the boundary's least value: spans fitted to the boundary make the healer spoil more faces (`OCC8228.stp` #10: 104 faces off their exact area, for 2) and abort on some parts (11 of 104 tried, on tori, in `SmSurfOfRevolution::MakeNurbWithSweepParams`; not reproduced with the torus alone). But SMLib's tessellator subdivides the whole of a face's surface domain down to the chord height, so on a surface very large for the deflection the turns are fitted all the same (a 3 cm face on a torus of 296 m, in the user's `VW.step`: 64 s and 7.8 GB for its part, 0.07 s and 73 MB fitted): where the pieces round, 2 pi over the angle a chord of the deflection's height spans, multiplied where both directions turn, pass 20,000. A whole turn's start a rounding error above -360 degrees is refused (`AdjustSTEPUVDomain`): taken as 0. Cones are built finite from the boundary's v range (SMLib's unbounded cones don't keep their surface under a shifted domain); a face past the apex, where Part 42's radius is negative, at the radius's size (the same points, half a turn round; Part 42's normal there still points away from the axis, its axial part turned). Edges take their intervals from their vertices: in closed form for lines and conics (each conic built over its edge's angles), by SMLib's `DropPoint` for B-splines. P-curves are dropped: SMLib makes the trims.
- **SMLib quirks the builder works around:** a line's vector is taken as a unit one (the builder normalizes it); a B-spline curve's knots must be clamped (`CreateCanonical` clamps); swept surfaces own their generator curve (deleting it corrupts the heap); extrusions are made infinite, and SMLib's exact areas of faces on them are wrong (4.3 for 76) until the surface is made finite (`AdjustSTEPUVDomain`, its STEP v 0 to 1 along the vector); extrusions and revolutions take B-spline generators (lines and conics converted exactly by `MakeExactBSplineIfPossible`), and a revolution turns a whole turn from where its generator lies, so the generator is turned to the boundary's least angle; a face reaching a closed periodic B-spline's seam (as a generator, or an edge across it) gets its trims on the wrong side of the seam, so such curves are extended by a period (Piegl and Tiller's periodic form) and trimmed to a period starting just before the face; the first loop is taken as the outer one, and files mark holes outer (`bug32049_sp7_04dx_242.stp`: 19 faces), so the builder puts first the loop reaching farthest. SMLib's torus refuses a major radius not above the minor (a spindle torus): such a face is built as the revolution of the arc of the tube's circle it lies on, the part outside the circle's crossings of the axis or the part between them (by which fits its boundary), over the boundary's v range. SMLib has no hyperbola or parabola: an edge on one is the rational quadratic Bezier arc between its vertices (the tangents' meeting point weighted cosh of half the parameter span). A face of only vertex loops on a sphere or torus is the whole surface (`CreateFaceFromSurface`). A cone face whose one loop goes round the axis without touching the apex is closed by the apex, which SMLib needs as a vertex loop (its exact area was a tenth to a half without: `bug24055_8MTF-75LS05.step`'s chamfers). SMLib can't trim a sphere face whose boundary passes a pole (the half-spheres of the `trj*_s1` files, bounded by circles about an axis square to the sphere's: 2 faces in each): the sphere is built about another axis, of the frame's and the loops' planes' normals the one whose poles the boundary stays farthest from (loops on one latitude not counted). Degenerate edges (flagged, or without a curve from a vertex to itself) are left out of their loops, a loop of nothing else a vertex loop (`bug26451_Test_STEP.stp`: 45 one-face parts). Edges whose vertices lie the other way along their curve than `sameSense` says (lines, B-splines) are built from end to start.
- **Orientation:** SMLib winds polygons about its surface's normal, and turns over those of a face whose upward side bounds a region other than the infinite one (`SmTess::OutputToPolyBrep`); the healer makes closed sheets solids, so that happens (every face against its surface in `trj2_io1-ct-203.stp` came out wrong before the rule). The builder records, per SMLib face after healing, whether to turn its triangles over: the model face's sense against SMLib's normal (compared at boundary points with Part 42's closed-form normals or, for swept surfaces, with the generator's tangent and the sweep; B-splines keep the model's parameterization), and again by that rule. A check for the healer turning a surface over found no case and was dropped.
- **Tessellating a copy:** `ConvertToPolyBrep` meshes a copy of the B-rep and maps polygons' faces back to the original, but not poly edges' edge uses, which dangle (reading them trapped): edges are found by their attribute, which the tessellator propagates.
- **Healing and the retry:** the healer is needed (without it, 60 of `bug32049_sp7_04dx_242.stp`'s 405 faces fail) but spoils some faces' meshes in their shells. So the wrapper judges every face's mesh area against SMLib's exact area and builds each face that fails `faceFailures`' rules, or is over 5% off (which the deflection may allow on a small face), again alone and unhealed, then, while that mesh fails outright or is over a fifth off, with SMLib's edge-length target at a half, a quarter and an eighth of the face's size (the root of its area; no less than a two-hundredth of its perimeter or twice the deflection, as a wrong exact area would otherwise ask for millions of triangles; and no further once an attempt gives nothing), keeping the closest mesh. A face still failing then (and of an exact area above zero) is built alone in further ways, in order, until one passes: healed; unhealed with the model's lengths times 1024; healed at that scale. Alone, some faces mesh only healed, some only unhealed, and some only larger: SMLib has absolute constants (below), so which faces mesh depends on the size of the numbers. A power of two, so that the model's points come back from the scaling as the same numbers. Never smaller: SMLib traps (a memory access out of bounds in the module) on parts made small, 53 of 80 of the user's parts in metres divided by 1024. Scaling SMLib's B-rep after it is built (`SmApiScale`) changes nothing, so the model is scaled before (`scaleModel`: a copy of the part's buffer with every length multiplied, parameters keeping their values; the transform brings the mesh back). A face without a mesh in its shell is tried alone even when it is smaller than the deflection squared, which `faceFailures` doesn't count as failing (59 faces of `bug24383_224013.stp` #11, all of which mesh alone, 51 healed and 25 unhealed). The edge-length target is used that sparingly because SMLib's refinement by it runs away on some faces (one of `bug31711.stp`'s, 8% off: 13 GB and no end). Each retried mesh is freed once copied, the measure going with the mesh kept (an info diagnostic counts them); the retried face's edges aren't shared with its neighbours'. A face the healer removes from its shell (slivers: 20 of a `VW.step` part's faces, each meshing alone) is retried the same way. Healing also splits a face at its seam into two SMLib faces of one row: judged and measured together (the first alone gave half the area: `bug31685_1.stp`'s cones). (Faces that first looked spoiled by healing, `trj7_k1-sd-214.stp`'s tori, spheres and cylinders, were our bug: an edge whose vertices weren't in order came back with its curve and no interval.)
- **Joining faces meshed apart** (`stitch`): SMLib's tessellator has no fixed-boundary mode (it splits every face's boundary edges again to that face's own subdivision: `SmTess::SplitFaceEdgesToUVSize`, `IsoEdgeSubdivide`), so a face meshed again alone has other points along its edges than its neighbours' meshes have, and the mesh was open along every edge of every such face (1,933 mesh edges of `OCC5099.stp` #14343, with 73 faces meshed again). The same holds between the shells of one body, each its own SMLib B-rep (`trj4_k1_top-ct-203.stp` #121: one body of 58 open shells, 14 edges open between them). The wrapper joins them afterwards, a placed item at a time (each B-rep carries its item's placement, `BuiltBrep::group`; an instance's placement is another; a closed shell is a group of its own, never joined to another shell along an edge they share, which would make it no longer closed: the user's rule, 2026-11-12, open shells sharing edges being one surface the file split, and such files to be normalized at load by later work), by topology and exact copies rather than by distance: each face's boundary segments are known by model edge (the poly edges' attribute) and meshing (each shell's, then each face alone). An edge two faces have is drawn as shared, though each face's own B-rep (a shell of its own, a face alone) has it free. First the edges' ends: on an edge's chain of segments in each meshing, the two ends are the model's vertices, and every meshing's vertex there takes the earliest meshing's position (the shell's before a retry's). Then each edge: the meshings' points put in one order along it (a point of one placed by the nearest segment of the others'; a ring's by turning it to the others' start), and each side's boundary segments split at the points it lacks, the triangle on each into a fan from its third vertex. Every point is one meshing's own, copied, so both sides have the same numbers; nothing moves but corners, and no triangle can turn over. The alternatives, the user's choice 2026-11-12: conforming the retried face to its neighbour one way (splits, then collapses of its own points, which can flatten or flip a triangle), or our own constrained triangulation in (u, v) (exact by construction, a new mesher). Where an edge can't be joined for its shape (a meshing's segments not one path or ring, a path against a ring, ends over twice the deflection apart) the shell's faces on it don't end at the model's vertices: they are meshed alone too, each way in turn until a mesh passes and meets the faces already meshed alone, and so on from them, each face once. **What is left is an error**, not a warning (the user's rule: a topological failure is an error; the mesh still comes back, and `tess-cache` holds such a result as a failure): "N edges along which the meshes of the faces they join don't meet", counted by position over the B-rep's whole mesh (a boundary segment on an edge two or more meshed faces use that only one triangle has; not by the attribute alone, which SMLib leaves off some faces' poly edges), so it also counts what SMLib's own shell mesh leaves open. Positions are compared as output, in single precision minus the origin: faces share no vertices in the result but by position, so that is what makes it watertight (in double, points that round to one float counted open: one edge of the user's `LMP1.step`, five of `Kuka.step`). **Folds:** SMLib sometimes makes two triangles on the same three points wound opposite ways, folding a face back on itself (at the corner it puts off the model's vertex on `trj3_s1-id-203.stp` #569's face #5003); the wrapper removes such pairs (together they cover nothing) and exact repeats, with an info diagnostic. The tests count the removed triangles too, as the removal would otherwise hide a face emitted twice. Known causes left: SMLib putting a face's corner off the model's vertex in every way it is built (`trj3_s1-id-203.stp` #569's B-spline face #5003, 1.7 mm: its two neighbours, meshed alone, are right), chains that are a path in one meshing and a ring in another, and points whose order differs along the two sides. `smlib_occt.ts` counts open model edges independently (from the results alone) for both backends; it finds model edges through the result's edge polylines, so it reports apart the shared edges without one, which it can't judge (16 of `Kuka.step` #4099's, where SMLib leaves the boundary segments without their edge's attribute).
- **The scale option** (`new SmlibTessellator({ scale })`, a power of two from 1 up): the whole part built with its lengths times the scale, results at the part's own size (judgements and measures divided back, the transforms carrying the inverse). Kept for small parts, and what the scaled retries are tested through; not a default (the user's decision 2026-11-12: lengths are to be converted to millimetres at load by other work, after which this is to be measured again).
- **SMLib's tolerances and scale** (measured 2026-11-12 on the 125 parts with faces missing then, 45 of the corpus's and 80 of the user's, `workdir/2026-11-11_smlib_failures/exp-all.txt`): SMLib derives a working "zone" tolerance from a model size estimate (`SmTol::SetModelSizeEstimate`, per context or B-rep; default 50 giving 1e-5, by bands 100 wide), but this release builds its old tolerance model (`SM_USE_OLDTOL` in `SmConfig.h`, the new one "not yet complete") with the new one's lines compiled in beside it. The healer takes its own estimate from the longest edge and sets the B-rep's tolerance from it, replacing the one the builder gives (the file's uncertainty: 2e-5 became 1e-6, 0.005 became 1e-5), and writes it into the shared context, where it stays for what is built next (so a face's retry can depend on what was built before it). Setting the estimate ourselves changed no result on any of the 125 parts; taking the tolerance from the estimate instead of the uncertainty was worse on the user's parts (117 faces missing for 89, 201 open edges for 90) and slightly better on the corpus's (67 for 76, 49 for 55). The large-to-small size ratio (`SetLargeSmallSizeRatio`) applies only to topology flagged small, a flag that exists only under `SM_USE_NEWTOL`: without effect in this build. What scale changes beyond the healer's band is the fixed constants (`SmMath.h`: `SM_EFF_ZERO` 1e-12, `SM_EFF_ZERO_SQRT` 1e-6, `SM_EFF_ZERO_PARAM` 1.2e-8), which only a patch could change: faces that fail unhealed, where the healer has no part, mesh when scaled. Whole parts 1024 times larger: on the user's parts (metres) faces missing 89 to 46 and open edges 90 to 48, on the corpus's (mostly millimetres) 76 to 80 and 55 to 51; one part 111 s for 2 s. Whole parts 1024 times smaller: 54 parts trapped. Per-face retries at both scales (as first built): the fewest faces missing (94 of both sets for 165) but the most open edges (330 for 145), a face that meshes only at another scale mostly not meeting its neighbours, and 15 parts trapped by the smaller scale.
- **Exact areas:** `SmApiFaceComputeArea` (to 1e-6 relative with measures, 1e-3 otherwise; a target, not a bound: 1.2e-6 on the seam cylinder), the perimeter by `SmApiEdgeComputeLength` (seams counted twice). Against the area oracle on the faces it trusts, more precise than OCCT's measures (61,195 of 61,526 within 0.1%, OCCT's 60,552), with a tail of gross errors (252 off by over 5%, OCCT's 37), not yet classified.
- **SMLib's triangulator** (`SmTess::TriangulateFace`): faces no subdivision node lies wholly inside (thin ones) are triangulated between their boundary points in (u, v), and on a face thin in space but not in (u, v) (15 mm by 0.5 mm of a torus of 56 and 2: 15 by 14 degrees) the diagonals join points far apart and leave the surface (47% more area than the face). Its own remedy is dead code in two ways: `TriangulateSingleFace` computes how often each new edge should be split but records it only when a singular edge was split too, and `TriangulateFace` then skips splits beside triangles thinner than 1 in 50 measured in (u, v), whose units differ (a torus's u runs 0 to 1, its v 0 to 360). A patch doing both right (the count always recorded, the aspect ratio measured on the surface) fixed that face but never finished on `bug29979_firetherm_12.step` #117536, with or without a cap on its rounds: not adopted, and no patch directory was made; the retry's edge-length target does it per failing face instead. `dMaxAspectRatio` has no effect on such faces.
- **Memory:** about 6 kB a triangle (the tessellator's own B-rep copy and poly B-rep): a part of 450,000 triangles takes 2.8 GB. The module may grow to 4 GB (`-sMAXIMUM_MEMORY`), pointers read unsigned in `index.ts`; past that the part fails with "out of memory". SMLib isn't sound above 2 GB in WebAssembly (`as1_motor.step` #1070, 3 GB natively, traps with a memory access out of bounds), which fails the part as running out did.
- **Meshes:** the chord height honoured (sampled centroids and edge midpoints within it) with fewer triangles than OCCT's (7.4 M over the corpus for OCCT's 31.2 M); the surface angle is SMLib's turning of the patch's control polygon, not an angle between triangles' normals.
- **Curve-bounded faces** (edges without vertices): each segment taken over its curve's own bounds (a trimmed curve's trims, a B-spline's range, a conic's whole turn), consecutive segments joined at a vertex made midway between their ends, one alone closed on itself; a segment on a trimmed curve against its basis is built along the basis and used the other way. Nothing fixes which way such a boundary runs (OCCT's `ShapeFix` orients them), so each loop is wound by its points' (u, v) on SMLib's surface (`DropPoint`): the outer loop counter-clockwise about SMLib's normal, the others clockwise (`wgehaeuse_surface.stp`, all curve-bounded: 204 faces of one part facing the wrong way and 112 unmeshed before, none and 1 after).
- **Not built yet** (warned of, the face or item left out), by what the corpus and the user's models hold (2026-11-12: every B-rep part's model of 502 of the corpus's 517 files and the user's 14, 5,159 parts, scanned for these kinds, `workdir/2026-11-11_smlib_failures/kinds.ts`; and the builder's warnings in the last `smlib_occt.ts` runs, which cover the parts OCCT meshes):
  - **In the files:** edges with p-curves only, without a 3D curve between their vertices (6 edges of one part, `bug22871_null-swept-curve.stp` #10, its faces left out); faces SMLib refuses on degenerate or unplaceable edges, a B-spline or line edge of no length, B-spline edges whose vertices SMLib can't place on the curve (one part each: `trj3_s1-al-214.stp` #6704, `bm2_pe_t4-B.stp` #877, `trj7_b1-ec-214.stp` #10: defects of the data OCCT tolerates); unbounded geometry, left out as it should be: a plane face without loops (`bug33665.step` #10), a loose plane (`tr8_ha1_db.stp` #346), loose lines (2 parts). What makes it more than sampling to the mesh's deflection: SMLib builds trims and heals at its zone tolerance (typically 1e-5, about 10,000 times finer than a 0.1 mm deflection), so a chord leaving a curved surface by the deflection reads as the edge off both faces, for the healer to widen tolerances, change the face or refuse it. Either sampled to the zone tolerance (thousands of points on a 10 mm circle, or a cubic B-spline fitted through far fewer), or the p-curve itself as an exact curve on the surface (SMLib's `SmCrvOnSurf`, which takes the p-curve in SMLib's parameterization: the same for B-spline surfaces, a conversion that isn't linear in general for elementary ones). With a polyline, the measures of the faces on such edges become approximate, by about the deflection times the edge's length.

- **Solid Core:** about 900 k lines of safe Rust, ported since 2026-10-12 (machine-assisted, its own docs say), unit by unit and checked against the C++ (554,873 cases, 0 failing, 4,186 deferred at stubs between units: 199 of 261 units green, 61 partial on 2026-10-23); no `unsafe`, no panics on bad input, deterministic, `wasm32-unknown-unknown` a target.
