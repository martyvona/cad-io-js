# Phase 4 (exporters and `stepconv`): plan and progress

*Paths in this document are relative to this `docs/` directory.*

Phase 4 of `architecture.md` ("Phasing"): the exporters, three.js JSON, then glTF/GLB, then 3MF, and the `stepconv` CLI that drives import, tessellation and export. The format table is in `architecture.md`, "Stage 4". This file tracks the order of work and what each step finds.

Status: **steps 1–4 and 3a done (2026-10-21); step 5 (3MF) written, under review.**

## Where things stand

- **The scene** (`../packages/cad-scene`): components placed by occurrences (a subassembly stored once), parts defined once, materials, layers, instance overrides, millimetres. `partInstances` expands the tree and resolves each placed part's material, per-face materials and visibility, top down as the CAx-IF practice has it. Meshes are `Float32` relative to a per-part origin, in the part's own unit, with face ranges, edges, wireframe curves and points (`phase3_progress.md`, step 6).
- **Tessellation:** `tessellateScene` (requests in parallel), the worker pool (`tess-workers`, timeout and recycling), the cache (`tess-cache`), and two backends, OCCT (robust, LGPL, 2.18 MB brotli) and truck (Apache, about 1/6 the size, less robust).
- **The CLI** (`../packages/cli`, `cad-io-cli`) has `step2json` only.
- **Nothing exports yet.** The corpus checks compare scenes and meshes against OCCT, but no file leaves the process.

## What every exporter needs

Three things the scene leaves to its consumers, the same for all three formats:

1. **Instances that differ in appearance.** All three formats share geometry between instances, but a mesh carries its materials (glTF: per primitive; three.js: a geometry's groups index the object's material array; 3MF: per triangle). Two instances of one part with different resolved materials (an assembly's colour applied top down, an instance override) need different meshes, or in three.js the same geometry with different material arrays. So each placed part reduces to a *look*: (part, material for unstyled faces, per-face materials). Instances with equal looks share one mesh.
2. **Splitting a mesh by material.** Face ranges with the same material become one primitive (glTF), one group (three.js) or one property id (3MF).
3. **The part's origin and unit.** A mesh is in the part's unit minus its origin, so each instance's transform is the part instance's transform times a translation by the origin; the unit is already in the part instance's transform.

A shared helper in `cad-scene`, `exportView` (step 1), computes the looks, their groups by material and the per-instance transforms once, and each exporter only writes its format.

## Decisions (made by the user, 2026-10-20)

1. **How glTF is written. Decided by the user (2026-10-20): glTF-Transform**, as `architecture.md` has it (MIT; `@gltf-transform/core` 4.5.1, one dependency, 1.8 MB unpacked): a tested writer, GLB packing, and later Draco, meshopt and `EXT_mesh_gpu_instancing` through its extensions, at the cost of a runtime dependency and a second document model beside the scene. (Alternative: written by hand; the JSON and GLB container are small and need no dependency, but compression later would bring one in or need our own code.)
2. **Edges, wireframe curves and points in the output. Decided by the user (2026-10-20): B-rep edges and wireframe curves each behind their own option.** three.js has `LineSegments` and `Points`; glTF has `LINES` and `POINTS` primitives (in the spec, but some viewers ignore them); 3MF has no lines, so neither option applies to it. (Alternatives: everything always; curves always and edges on request; one option for all.) **Both off by default** (the user, the same day), so wireframe-only parts export empty unless curves are turned on; isolated points go with the curves option, since both come from wireframe representations.
3. **3MF meshes that aren't manifold.** Surface models, open shells and parts the backend meshed with gaps (truck's empty faces, say) break the core spec's rules for `model` objects. 3MF 1.4 allows `surface` and `other` objects to break them (core spec, section 4.1). **Decided by the user (2026-10-20): each welded mesh is checked; by default the ones that fail are left out with a warning, and a `stepconv` flag (and the matching exporter option) writes them as `surface` objects with a warning instead.** (Alternative: everything written as `model`, left to the slicer.)
4. **`stepconv`'s default backend. Decided by the user (2026-10-20): OCCT, with truck by option.** OCCT is the more robust (the reference in every check), truck the smaller and Apache-licensed; the CLI runs in Node, where download size doesn't matter. (Alternative: no default, the backend always named.)

Not proposed for this phase: Draco or meshopt compression and `EXT_mesh_gpu_instancing` ("optional later" in `architecture.md`), the 3MF Production extension (open item in `architecture.md`), and per-curve colours (backlog).

## Step 1: the export view

`../packages/cad-scene/src/export.ts`, `exportView(scene, meshes, {edges, curves})`:

- **Looks:** each placed part's appearance comes from `partInstances`, so the CAx-IF rule (overrides, then the topmost component's material, then the part's with its per-face materials) stays in one place. A look is a part plus the material of each of its mesh's face ranges (its own, else the instance's) and the default material, which edges, curves and points take. Face materials of faces the mesh doesn't have don't split looks. Instances with equal looks share one.
- **Groups:** a look's triangles reordered so faces with the same material are contiguous, groups in order of first appearance; a mesh with one material keeps its own index array, and a mesh without face ranges (a future mesh part) is one group.
- **Nodes:** the expanded instance tree as `instances` walks it (a component inside itself isn't expanded again), each node with its occurrence, its name (the occurrence's, else the component's), its local transform, and its parts as looks with the part reference's transform times the translation by the mesh's origin, and visibility.
- **What's dropped:** parts with nothing to draw: no mesh (failed or not tessellated), or only edges, curves or points when their option is off (decision 2, both off by default). Hidden part instances are kept, marked `visible: false`, for each exporter to decide.
- `partMesh` gives a part's mesh: its tessellation, a mesh part's finest level, or a curves part as a curves-only mesh.

## Step 2: three.js JSON

`../packages/export-threejs` (Apache-2.0; depends on `cad-scene`; three 0.186.1 and its types as dev dependencies, for the tests and the corpus check):

- **`threejsChunks(scene, view, opts)`** yields the JSON Object Scene format 4 document (version 4.7, as `Object3D.toJSON` writes it) in chunks, since the arrays are plain JSON numbers and a large model's JSON can exceed V8's maximum string length; `threejsJson` joins them for small scenes. Floats are written in the fewest digits that read back to the same `Float32` (`formatFloat32`), and uuids are deterministic, so the same scene gives the same file.
- **Objects:** a root `Group` (`userData`: `unit: 'millimetre'` and the scene's properties); a `Group` per node of the view's tree, with its local matrix (both column-major, written as is) and `userData` with the occurrence's sources and properties, the component's index, name, sources and properties, and any external reference; per placed part a `Mesh` (a `Group` for a part without triangles) with the part's matrix, `visible: false` for hidden instances, and `userData` with the part's index, sources, properties and its faces' sources as index ranges (`Look.faces`, added to the export view for picking). Lengths are millimetres and axes as in the source (`architecture.md`'s "keep file units": the scene's unit since phase 2).
- **Lines and points** (decision 2, each on request): B-rep edges and wireframe curves as `LineSegments` children of the part (polylines turned into segment pairs, so one geometry holds all of a part's edges; `userData` lists each polyline's source, kind, dihedral and index range), points as a `Points` child (`userData`: their sources).
- **Geometries** are shared by every instance of a look, and by looks with the same triangles; a look with one material reuses any geometry of its mesh, with its material repeated for each group, so an instance recoloured by an override doesn't repeat the vertices. A geometry with several materials has `groups` indexing the `Mesh`'s material array.
- **Materials:** one per scene material and kind: `MeshStandardMaterial` (three's defaults otherwise), `LineBasicMaterial`, `PointsMaterial`; colours are the scene's sRGB as hex, which is how three's JSON stores colours; opacity below 1 sets `transparent`; `userData.material` is the scene material's index.

## Step 3: `stepconv`

`../packages/cli/src/stepconv.ts` (bin `stepconv`), structured like `step2json` (`Io` streams in, an exit code out: 0 done, 1 usage, 2 failure with nothing written, 3 parts that failed with `--strict`):

```
stepconv [options] <file.stp | file.stpZ | -> -o <output>
  -o, --output <file>      the output file ('-': standard output, with --format)
  -f, --format <format>    threejs (.json); glTF/GLB and 3MF with steps 4 and 5
  -b, --backend <name>     occt (default, decision 4) or truck
  -d, --deflection <mm>    default 0.1        --angular <deg>   default 28.6, exactly the library's 0.5 rad (truck ignores it, phase 3 decision 2)
      --edges, --curves    B-rep edges; wireframe curves and points (decision 2: both off by default)
      --double-sided       three.js faces from both sides
  -j, --workers <n>        default cores - 1; 0: on the main thread, one part at a time, no timeout
      --timeout <s>        per part, default 120 (0: none)
      --cache <dir>        a tess-cache FileStore; --cache-size <MB>, default 1024 (0 disables)
      --strict             exit 3 if a brep part isn't tessellated (the output is written all the same)
  -q, --quiet, -h, --help
```

- **The path:** `readStep` (plain or gzipped, file or standard input) → `importStep` → `tessellateScene` over a `tess-workers` pool of the backend (or the backend itself with `-j 0`), wrapped in a `CachedTessellator` with `--cache` → `exportView` → the format's writer, its chunks written with backpressure. The root object is named after the input file (`stdin` for standard input).
- **Output:** opened after the import and before tessellating, so a bad path fails at once (exit 2); on a later failure the partial file is removed.
- **Summary** on standard error (unless `-q`): parts (brep parts tessellated), placed parts, triangles, bytes written; import, tessellation and export times; cache hits and misses with `--cache`; error, warning and note counts and the first 20 errors and warnings, as `step2json` lists them. A progress line (`tessellating n/total`) when standard error is a terminal. Parts that fail don't fail the run (they're in the summary, as in `step2json`) unless `--strict`: then a brep part without a mesh makes the exit code 3, after the output is written. A part whose result is empty gets no error of its own (`tessellateScene` leaves it out of the meshes; the test's broken cube shows 0 errors and OCCT's one warning), so the count of parts tessellated is what `--strict` goes by.

**Found on the way: OCCT's messages on standard output.** OCCT prints messages (`*** ERR StepReaderData : ...`) through Emscripten's `print`, which is `console.log`, so with `-o -` they landed in the middle of the JSON (`bug32314_corrupted.stp` and others, on the main thread and in workers alike, since a worker's standard output is the process's). First fixed by sending them to standard error; then, at the user's review, kept as diagnostics instead (below).

**OCCT's messages as diagnostics** (the user, 2026-10-20: printed nowhere; kept per part if they're informative, within a memory limit). ## Step 3a: dangling references (a detour, decided by the user 2026-10-21)

Step 3's survey of OCCT's messages found references to instances the file doesn't define that the importer didn't report, in 4 corpus files; OCCT's warnings counted them, without ids, and only with the OCCT backend. The importer already had what it needed: each part's closure (`closure`, computed at import for the origin and faces), and the scan's index of references.

- **`danglingRefs(file, positions)`** (`step-parser`, `subset.ts`): the ids that instances at those positions refer to but the file doesn't define, once each, ascending.
- **The importer** warns once per part with any: `13 references to instances the file doesn't define: #11, #393036, ..., #393179, ...` (at most 10 named, `MAX_DANGLING`), or `1 reference to an instance the file doesn't define: #18`, with the representation as the source. Parts only: elsewhere a dangling reference doesn't change the geometry, and `step2json --check` already reports every one in the file.
- **References beyond the largest id** (`#18446744073709551615` in `bug31292.stp`): the scan leaves them out of its index (so they can't wrap around to a small id), and so out of `danglingRefs`; it warned of nothing, and the decoder warned only when an instance was decoded with a `warnings` list (`step2json --check`, not the importer). Now the scan warns, once per reference, with the instance's id (`reference beyond the largest instance id (2^32 - 1) read as $`), and the decoder no longer does, so `--check` doesn't list it twice. That is a file warning rather than the part's: the scan doesn't know the parts.

**Corpus** (`../corpus_checks/dangling_refs.ts`, log `dangling_refs.log`, 16 s): 53 parts of 3264 in 4 files of 517 with dangling references, and 1 reference beyond the largest id. ## Step 4: glTF/GLB

`../packages/export-gltf` (Apache-2.0; dependencies `@gltf-transform/core` and `@gltf-transform/extensions` 4.5.1, MIT, pinned; dev dependency `gltf-validator` 2.0.0-dev.3.10, Apache-2.0): `gltfDocument(scene, view, opts)` builds a glTF-Transform `Document`; `glb(...)` gives GLB bytes, `gltfJson(scene, view, bin, opts)` the `.gltf` JSON and its buffer, which the JSON names `bin` (with `bin` undefined, the buffer embedded in the JSON as a base64 data URI). ### Survey before the exporter: welding OCCT's meshes

| Welding | closed | open | misoriented | non-manifold | degenerate triangles dropped |
|---|---|---|---|---|---|
| exact | 1142 | 1950 | 5 | 28 | 50,370 in 407 parts |
| 1e-7 of the diagonal | 1144 | 1931 | 21 | 29 | 52,321 |
| 1e-5 of the diagonal | 1129 | 1921 | 23 | 52 | 91,128 in 422 parts |

- **Open meshes are open shells in the file.** With exact welding, 1940 of the 1950 open meshes have free B-rep edges; only 10 are open without any (gaps in OCCT's mesh). - **Misoriented:** 5 meshes, all with free edges (`wgehaeuse_surface.stp`, `trj5_k1-ec-214.stp`): closed by count, but with faces reversed against their neighbours.

### lib3mf, tried before use

`@3mfconsortium/lib3mf` 2.5.0-fix.2 (the `latest` tag, February 2026; BSD-2-Clause; 2.2 MB `.wasm`) loads in Node 24: `CWrapper`, `CreateModel`, `QueryReader('3mf')`, `ReadFromFile` on a file in its Emscripten file system (`Module.FS.writeFile`; `ReadFromBuffer` needs a pointer the module doesn't export `malloc` for), `GetWarningCount`/`GetWarning`, `GetObjects`, `IsManifoldAndOriented` per mesh object, the object type. On hand-made files it accepted a tetrahedron with `basematerials`, components and a mirrored component transform, reported an open and a flipped tetrahedron as not manifold and oriented (read without error or warning), and refused a triangle with a repeated vertex.

### From the specs

- **Core 1.4.0:** mirrored transforms are allowed (a consumer keeps the volume's sign); a `model` mesh needs at least 4 triangles; triangles' indices distinct (zero area only "SHOULD NOT"); an object with triangle properties MUST give `pid` and `pindex` as their default; component objects MUST NOT have `pid` or `pindex`; items MUST NOT reference `other` objects; producers SHOULD collect objects that must keep their relative placement as components of one object, since consumers MAY rearrange build items.
- **Colours:** `basematerials`' `displaycolor` (sRGB with alpha) is "for rendering purposes only"; "for specifying the color design intent for a printed part, a producer MUST specify color properties via the material and property extension" (core, chapter 5). That extension's `colorgroup` colours are opaque; a translucent effect needs `multiproperties` with translucent display properties (Materials and Properties extension, chapters 2 and 7).

### Decisions

1. **Colours. Decided by the user (2026-10-21): `basematerials` by default, `colorgroup` by option.** By default one `basematerials` group, a base per colour with its sRGB `displaycolor` and alpha (core spec only; display colour, transparency kept); an exporter option and `stepconv` flag write a `colorgroup` (the Materials and Properties extension) instead, opaque colours as print intent, transparency dropped. (Alternatives: either one only; `colorgroup` by default.)
   The Materials extension, when used, is **not listed in `requiredextensions`** (the user, the same day): its namespace is declared only, so a consumer without it can still read the geometry, without colours. (Alternative: required, so such consumers refuse the file.)
2. **The build. Decided by the user (2026-10-21): a build item per placed part by default, and the assembly as one item by option.** By default each placed part is an item referencing its mesh object at its world transform, so slicers may arrange the parts apart as separate prints; with an exporter option (and `stepconv` flag) one item for the whole scene, an object whose components follow the instance tree (as planned), so the assembly keeps its placement (the core spec: consumers MAY rearrange items, and producers SHOULD collect objects that must keep their relative placement as components of one object). In the parts build the tree is kept in each item's metadata, its path of instance-tree names; the core spec makes an item's `partnumber` "a unique identifier for the item", so it holds the instance path (as indices), and the part's number goes on the part's mesh object (`partnumber`, "part number"). Metadata names outside the spec's list (title, designer and so on) need a namespace declared on the model (core 3.4.1), so ours have one of their own. (Alternatives: one item for the scene; an item per root of the tree; an item per part with metadata only, or with unreferenced component objects too.)
3. **Hidden part instances. Decided by the user (2026-10-21): left out with a warning by default; an option (`stepconv --keep-hidden`, as for glTF) writes them as ordinary parts.** 3MF has no visibility. (Alternatives: always left out; always written.)
4. **Names. Decided by the user (2026-10-22), in the importer, so for every consumer of the scene:** a part whose name is generic (blank, `NONE` in any case, or `#` and digits, as some writers name representations after their instance ids) takes the name of the first product placing it, unless that is generic too; a blank product name gives way to its part number (STEP's product id); a blank occurrence name is no name, so nodes take the component's (the products extractor already drops blank occurrence names). Other names are kept as they are (264 parts have names of their own that differ from their product's, such as `GBWSR1` and `GBSSR1` in a product named `Product`), and common words such as `SOLID` or `SHELL` aren't generic (some files use them as names). (Alternative: a part always named after its product when one product places it.) In the corpus: of the 136 parts with a generic name whose product had a real one, 134 now take the product's (`#609` → `l-bracket`, say); the 2 left are named `solid` (`trj5_k1-sh-203.stp`) and `1` (`bug25013_25013face.stp`), outside the list. 50 components with a blank name now carry their part number.
5. **Inside-out closed shells. Decided by the user (2026-10-22): turned over, but only where they can't be the boundaries of voids, and in the in-memory meshes (`tessellateScene`), not in an exporter.** The user's principle: the library is also for loading CAD data into memory and recovering names, orientations, hierarchy and transforms as well as possible, so fixes for imperfect input go into the scene and its meshes, independent of any exporter. `cad-scene`'s `orientShells` (in `../packages/cad-scene/src/mesh.ts`, with `weld` and `manifoldProblems`, moved there from `export-3mf`) splits the welded mesh into connected pieces and turns over each one that is closed, oriented and of negative volume, unless another piece may enclose it: a closed piece that a ray from one of its vertices crosses an odd number of times in any of three directions, or an open piece whose bounding box contains it. Triangles are rewound, and normals reversed where they followed the winding (OCCT's for surface models) but not where they already point out (the tessellated parts' own). `tessellateScene` applies it to every mesh, with a warning per part (`n closed shells turned over (inside out, and inside no other shell)`); `orient: false` keeps the backend's meshes as they are (the weld survey uses it, to measure them before any fix). The 3MF exporter's own check still fails an inside-out mesh handed to it directly. Format requirements stay in the exporters: welding is what 3MF's encoding needs (see 6 for degenerate triangles). (Alternatives: in the export view, as first written, which only the exporters see; not turned.)
6. **Degenerate triangles. Decided by the user (2026-10-22): dropped in the in-memory meshes (`tessellateScene`), not only by the 3MF exporter; vertices not merged there.** `cad-scene`'s `dropDegenerate` removes triangles with two corners at one position (exactly equal `float32` coordinates, −0 as 0, or one vertex used twice). They cover nothing; in a welded mesh they would join pieces that only touch there (the gap `orientShells`'s mutation check found); and removing one never opens a mesh, since its two other edges are one edge both ways. Slivers with three distinct corners on a line stay, since their long edge is also a neighbour's and dropping them would open the mesh. Faces keep their entries, with fewer triangles (perhaps none), so the face list still maps to the B-rep; vertices, normals and edges are shared with the backend's mesh (vertices only dropped triangles used stay, unused). It runs before `orientShells`, with an info diagnostic per part (`n degenerate triangles dropped (two corners at one position)`); `dropDegenerate: false` keeps them (the weld survey uses it too). Merging vertices stays out of the stored meshes: the backends split vertices at face boundaries on purpose (normals at sharp edges, vertices per face), so a welded mesh is a view of the topology, which `weld` gives to whoever needs it (3MF; an STL writer or a closed-mesh check later). The 3MF exporter still drops any degenerate triangles it finds, for meshes made with `dropDegenerate: false`. (Alternatives: in the exporters only, as first written; also zero-area slivers; also merging vertices with equal position and normal, which loses nothing but repairs nothing and only shrinks the glTF and three.js meshes, unmeasured.)

### The exporter

`../packages/export-3mf` (Apache-2.0; dependency `fflate` 0.8.3, MIT, pinned; dev dependency `@3mfconsortium/lib3mf` 2.5.0-fix.2, BSD-2-Clause): `threemf(scene, view, opts)` gives the zip in pieces and diagnostics. Options: `defaultColor`, `name` (the model's title), `colors: 'basematerials' | 'colorgroup'`, `build: 'parts' | 'assembly'`, `nonManifold: 'omit' | 'surface'`, `hidden: 'omit' | 'keep'`.

- **Meshes:** each part mesh welded once (`cad-scene`'s `weld`: equal `float32` coordinates, −0 as 0, an open-addressing table on the coordinates' bits), triangles welding made degenerate dropped (an info diagnostic with the count; none in meshes from `tessellateScene`, which dropped them, decision 6), only the vertices a kept triangle uses written. `manifoldProblems` checks what a `model` object must be: every edge in exactly two triangles in opposite directions (boundary, non-manifold and misoriented edges counted), at least 4 triangles, and positive volume. A mesh object per look (an object carries its triangles' properties, so looks can't share one), vertices in the part's unit relative to its origin, as the scene has them; the transforms scale and place them. Vertices as the shortest decimal that reads back as the same `float32` (`float32Text`), transforms as shortest doubles.
- **Failing meshes** (decision 3 of the plan): a warning per part (`part '<name>' is not a closed, oriented manifold (<problems>); left out`, the part's source as the diagnostic's), or with `nonManifold: 'surface'` (`stepconv --3mf-surfaces`) written as `surface` objects.
- **Colours:** one property group, id 1: `basematerials`, a base per scene material used (named after the material, else its `#RRGGBB`, `default` for the default colour; names made unique), `displaycolor` with alpha; or the Materials extension's `colorgroup` (`stepconv --3mf-colorgroup`), opaque, a warning when a transparent material was used. Every object has `pid`/`pindex`, its largest group's; triangles of other groups have `pid` and `p1`.
- **Build:** an item per placed part (decision 2) at its world transform, `partnumber` the node's index path and the part's index in it (`0.2.1:0`), metadata `cadio:path` the names from the root to the part (namespace `urn:cad-io-js:3mf`). With `build: 'assembly'` (`stepconv --3mf-assembly`): a components object per instance-tree node with something written (its parts' objects at their transforms, its children's objects at theirs), identical ones shared (same name, same components), and one item: the root's object, or for several roots an object over them named after the model.
- **Model:** `unit="millimeter"`, `xml:lang="und"`, metadata `Title` and `Application`; the object's `name` the part's, `partnumber` the part number of the first component placing it. The model part is written and deflated in pieces of about 1 M characters (fflate's streaming `Zip`), so no string near V8's limit; zip entries dated 1980-01-01, so the same scene gives the same bytes.
- **`stepconv`:** format `3mf` (`.3mf`; standard output works); `--3mf-colorgroup`, `--3mf-assembly`, `--3mf-surfaces`; `--keep-hidden` now applies to 3MF too. The `--3mf-*` options with another format, and `--edges`, `--curves` or `--double-sided` with 3MF, are usage errors.

**Found on the way (lib3mf 2.5.0; workarounds in our code, no upstream report):**

- **Numeric character references refused.** lib3mf refuses `&#38;` and the like ("XML contains an invalid escape character"), valid XML though they are; it reads the named entities. So only `&amp; &lt; &gt; &quot;` are written; in attributes, tabs and line breaks become spaces (which XML's attribute normalization makes of them anyway); in element content they are written as they are.
- **A triangle's `p1` without `pid` ignored.** The core spec lets a triangle give `p1` alone (its `pid` "if different than the property group defined at the object-level"); lib3mf then gives the triangle the object's property. Found by the tests (every triangle read back in the object's colour). Triangles whose property differs from the object's now carry `pid` too.
- **Transforms read as `float32`.** lib3mf's `sTransform` has single-precision fields, so the checks compare transforms to `float32`; the file has them as shortest doubles.
- **Its manifold check ignores orientation's sign.** `IsManifoldAndOriented` passes a closed mesh that is inside out (negative volume); the core spec's outward-normals rule fails it. Ours fails it, and the corpus check computes the volume itself.

Choices made here, for the user's review:

| Choice | Made | Alternatives |
|---|---|---|
| Welding | exact (equal `float32` coordinates), as the survey supports | within a tolerance |
| Degenerate triangles | dropped in `tessellateScene` (decision 6, the user's); the exporter drops any left, with an info diagnostic | (none: the spec forbids repeated indices) |
| Object per look | each look its own vertices (a property is per triangle) | a part's looks sharing an object, colours per instance lost |
| Vertex precision | shortest `float32` text, exact | fewer digits (smaller files) |
| Part numbers | object: the first placing component's part number; item: the instance path | none on items |
| Unit | millimetre, vertices in the part's unit scaled by the transforms | vertices in millimetres (transforms without scale) |
| Lines and double-sided faces with 3MF | usage errors in `stepconv` | ignored silently |
| Compression | deflate level 6 | level 9; stored |
